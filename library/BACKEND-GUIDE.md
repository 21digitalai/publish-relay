# Publish Relay Backend Guide

Fanvue account-scoped reads use the selected connected account and its workspace-bound creator grant. Credential refresh failures are typed as reconnect-required and become a safe 409 read response; pending single-use refresh may be awaited, but a read must recheck that the exact account and connection remain active before sending the provider GET. An invalid or ambiguous refresh never replays the quarantined refresh token or becomes an unclassified 500.

## Fanvue publishing connection foundation

`fanvue-post-client.ts` is the provider POST transport for the documented `POST /v1/posts` API version `2025-06-26`. It accepts only explicit audience, text, stable Fanvue media UUIDs, attached preview UUID and optional provider price in USD cents; paid posts require attached media and Fanvue's documented 300-cent minimum. It never retries. Only HTTP 201 plus a validated response confirms creation; network loss, HTTP 5xx, unexpected 2xx or an unparseable 201 produce `FanvuePostOutcomeUnknownError`, requiring durable reconciliation before any resend. This transport alone does not dispatch jobs: the scheduler must first reserve attempt intent, prove the selected tenant/account, required grant and ready media, then persist the provider result or unknown outcome. The reviewed publishing grant now includes `read:media` for provider readiness and `read:post` for API readback; production activation still requires the app allowed-scope plan and controlled consent proof.

Fanvue multipart signed-part responses are bounded to 256 and must match the requested inclusive part-number range exactly, without duplicates. Missing or mismatched provider parts fail closed as an invalid response before uploading bytes; signed PUT requests never carry the creator bearer token.
`fanvue-media-upload-plan.ts` derives the bounded one-based upload ranges from the local media byte size and provider session part size. Session creation rejects a provider `totalParts` or `maxParts` that cannot cover the exact media size, including an impossible >256-part upload, before any signed-part PUT. The final range may be shorter; later staging must read only that bounded range and persist the confirmed ETag before advancing durable progress.
`fanvue-media-part-stream.ts` consumes one hash-verified local range stream starting at the durable next part and yields exact sequential Buffers without rehashing the full media file for every part. The session is rejected if its part size exceeds the 16-MiB local buffering bound; short/overlong source streams fail closed. The uploader must consume one yielded part at a time and persist each confirmed ETag before asking for the next part.
`fanvue-job-media-source.ts` resolves ready media only through the exact leased Fanvue publication job, its immutable revision attachment, selected workspace, lease owner and strictly unexpired `lease_expires_at`, before any provider upload attempt exists. It opens `MediaStorage.openVerifiedRange` once from the durable byte offset to the verified file end; absence, invalid offset or hash mismatch fails closed. Later staging must recheck the lease/attempt boundary before any provider mutation and keep the stream inside the artifact lock; this source helper alone performs no upload or durable progress write.
`fanvue-upload-session.ts` defines the encrypted credential payload for uploadId, media UUID, exact part plan and ordered ETags. It rejects gaps, duplicate parts and corrupted receipt order; each append computes the corresponding next byte offset. `fanvue-upload-progress.repository.ts` first verifies the caller's proposed part/session against the encrypted credential actually stored for the selected tenant, then reserves a durable `put_pending` part intent under the exact job/media/artifact/lease before any signed PUT; duplicate reservation or automatic retry is refused. Only a confirmed PUT receipt may transition that pending part back to `uploading` while atomically rotating the encrypted ordered session and advancing its matching offset. A crash or ambiguous PUT remains pending for explicit reconciliation, never blind resend. The CAS requires the active artifact, credential version, unexpired worker lease, active Fanvue account and no publication attempt, and rolls back the artifact update if credential rotation fails. Artifact and lease expiry compare to PostgreSQL's clock at the write, never a stale caller timestamp. `fanvue-upload-part.service.ts` holds the artifact lock for one exact bounded verified source range, requires Fanvue's signed part size to match the durable session plan, signs only that part, reserves the intent before its signed PUT, and settles only a confirmed ETag; it does not retry an uncertain PUT. Full session creation, readiness and worker dispatch remain separate orchestration steps.

`fanvue-media-staging.service.ts` preflights the selected leased job/media and reserves the canonical 24-hour job/media artifact before session creation. The dedicated guarded INSERT SELECT in fanvue-artifact.repository.ts checks the current PostgreSQL clock, selected Fanvue account, leased job, ready immutable-revision media and absence of attempts atomically; a cancellation, expiry or disconnect after preflight cannot leave an orphan initialized artifact. A same-provider initialized artifact left between reservation and session intent is reused only after a fresh job/account/media/lease/attempt check; a foreign-provider, pending, or ineligible artifact is refused rather than re-created. `fanvue-upload-init.service.ts` accepts that initialized artifact, resolves its tenant/lease-bound ready media metadata, and allows only supported local MIME types. Under the artifact lock, it reserves `session_pending` before one provider create-session call, then persists the exact returned part plan as an encrypted artifact credential. The reservation validates selected Fanvue account, immutable revision attachment, ready media and absence of post attempts in one tenant transaction. A lost create response remains pending and is never retried automatically; a confirmed session receipt may still be stored if the lease expires while the provider call is in flight. A pending artifact cannot infer a new session.
`fanvue-upload-completion.service.ts` takes the same artifact lock and reserves `complete_pending` against the exact encrypted full session and leased job before one provider PATCH. Only a PATCH response with the shared allowlisted `processing` or `ready` status records the media UUID and enters local `processing`; an error/unknown status or lost response remains pending for explicit provider-status reconciliation, never a blind repeat. `fanvue-upload-readiness.service.ts` reads the exact selected processing artifact and rechecks the leased job/media source before a provider status GET; only a matching ready media UUID may CAS that artifact to `finalized`. Processing stays pending, provider error or identity mismatch fails closed, and no post is attempted here. Worker dispatch and ambiguous completion reconciliation remain separate orchestration steps.

The destination-first Fanvue admission shape is `kind: "post"`, explicit `audience`, optional `text`, local `mediaIds`, optional attached `mediaPreviewId`, and optional integer USD-cent `price` (minimum 300, media required). `publication-target.ts` validates and preserves these inputs. `fanvue-post-payload.ts` consumes that same schema and maps only supplied provider-ready UUIDs for every attached media and preview; a missing or invalid provider UUID fails before post creation. The worker must obtain that map from exact job/media-bound finalized artifacts rather than caller data. This mapper alone does not enable the Fanvue destination capability or send posts.

Once Fanvue media is processing or finalized, its durable provider UUID is authoritative and no upload-session decryption is needed; only the uploading phase requires the encrypted part state. A pending external session/PUT/completion intent becomes an explicit unknown publication attempt marked for staging reconciliation with no post sent, rather than a repeated retry_wait loop. Definite pre-post validation/staging failures finish as failed, while a typed creator reconnection failure finishes as auth.

`fanvue-stage-job-media.service.ts` resumes only confirmed upload progress for the selected leased job/media: it may create a new session from an initialized artifact, upload one recorded part at a time, complete once, and poll processing status until finalized. The exact tenant-bound artifact read decrypts the durable session; session/PUT/completion pending phases refuse automatic replay. It returns processing instead of dispatching a post with unavailable media.

A definite prior Fanvue post rejection (rate limit, auth, validation, transient or permanent) may reuse its exact finalized media artifact for a safe retry while the artifact remains active. An unfinished, unknown, accepted or published attempt bars further staging and map reads; provider media is never re-sent automatically after a possibly successful post.

`buildFanvueEffectivePayload` is the canonical target-admission projection: it validates the explicit Fanvue post shape, local attachment order, provider-supported image/video MIME types, free versus native price, and preview membership before storing the job effective payload. Worker claims filter on that persisted `kind: post` rather than reconstructing a draft. The canonical destination capability snapshot advertises `post` with bounded media count; the destination-first browser Composer requires that same kind before submitting through the canonical workflow route. Provider activation remains subject to independent integration and controlled live proof.

`fanvue-post-dispatch.service.ts` claims due Fanvue post jobs on the canonical worker, loads only the selected active creator and exact ready revision attachments, refreshes publishing consent, stages each media to finalized provider UUID, and defers processing/pending staging before any post attempt. It reserves durable publication intent with a last in-transaction creator/media preflight before exactly one provider POST. Confirmed 201 stores the provider post UUID; 400/401/403 are definite failures, 429 is bounded retry, and transport/5xx/invalid success remains unknown with a reconciliation key and no automatic resend. No permalink is invented from the UUID.

`getFinalizedFanvueMediaUuids` reads provider UUIDs only from finalized, unexpired artifacts attached to the exact selected Fanvue job revision while its lease and account remain active and no post attempt exists. The post payload mapper still rejects any missing UUID, so a partial map cannot authorize a post.

`fanvue-media-upload-client.ts` is the separate provider multipart transport: open `/media/uploads` under `write:media`, sign a bounded part range, PUT bytes to a provider-signed HTTPS URL with no Relay bearer token, complete with part ETags, and query `/media/{uuid}` status. The signed URL and variant URLs are ephemeral and never durable identifiers; only the returned media UUID may be linked to a local revision/job through the existing `provider_staging_artifacts` lifecycle. This transport does not read local media, persist staging artifacts, poll without bounds, or enable publishing by itself.
Fanvue top-level comment creation uses `fanvue-comment-client.ts` as a transport-only boundary for the documented creator-owned `POST /v1/posts/{uuid}/comments`. It accepts text of 1–600 characters and projects only comment UUID, text and timestamps. There is no documented parent-comment parameter, so this is never labeled a threaded reply. Definite 400/403/429 responses are classified failures; fetch failures, 5xx and malformed success remain unknown outcomes and may not be blindly retried. `fanvue-comment.service.ts` owns the account-scoped send command: it validates input, asks the selected-account read service to prove creator-owned post reach and both `read:post`/`write:post`, enforces the neutral `engagement.send` action policy for the authenticated actor, reserves the exact action ID and request fingerprint before one POST, then settles the provider UUID, definite 4xx, or unknown result. Replays return ledger state without a second send; a failed settlement leaves the reserved intent ambiguous. The machine `POST /api/v1/fanvue/accounts/:accountId/posts/:postUuid/comments` requires distinct `fanvue:comments:send` API-key/delegated scope and mutation rate limit. Its bounded body is text plus clientActionId; the only result fields are state and confirmed comment UUID or definite failure status, with no provider token, post body, fan identity or internal ledger fields. This machine route is not browser approval, live-send authorization, or a released provider capability.
Fanvue one-to-one chat sending uses `fanvue-message-client.ts` as a transport-only boundary. It validates the documented `POST /chats/{userUuid}/message` text, ready-media UUID, USD-cent price (minimum 300), and attached free-preview shape; it pins API version `2025-06-26` and returns only the stable `messageUuid`. Definite 400/403/429 failures are classified as provider errors. A fetch failure, 5xx, unexpected status or malformed 201 response is an unknown send outcome, never permission to resend. `fanvue-message.service.ts` composes the selected-account existing-chat and `read:chat`/`write:chat` preflight, neutral `engagement.send` action policy, durable action ID reservation before one POST, and confirmed/definite-failure/unknown settlement. For already-uploaded provider media selected through the account-scoped media read tool, it rechecks each stable UUID is `ready` on that exact selected account before accepting free or native priced/preview send. Local Relay media ID to provider media upload/staging is still a separate acceptance slice; no local asset is silently treated as a ready Fanvue UUID. Neither service nor transport grants chat consent or a live provider release.

`fanvue_action_intents` is the tenant/account-bound, pre-provider-call reservation shared by future one-to-one message and top-level comment commands. A `clientActionId` is unique per account; exact replay returns its existing reserved/confirmed/failed/unknown state, while a changed action kind, target or fingerprint conflicts. The reservation must commit before POST, so a process death after reservation leaves a conservative ambiguous state. Only the original sender settles a reserved row. The existing API/browser mutation-result ledgers cannot substitute for this boundary because they roll back the insert when the provider call fails. Migration 0079 owns the table and forced tenant RLS. This ledger is not an offer-matching or approval-policy layer.

Migration 0089 extends the same intent ledger with `chat_create`. `POST /api/v1/fanvue/accounts/:accountId/chats` takes only the selected fan UUID and client action ID under `fanvue:chats:send`; it resolves the exact creator account and `read:chat`/`write:chat` grant, enforces `engagement.send`, reserves a durable intent, then makes one documented `POST /chats` with `{userUuid}`. Fanvue returns only a success message, not a chat ID, so the confirmed projection retains the selected fan UUID. A provider 400 is surfaced as not contactable, while ambiguous transport/5xx remains unknown and is never replayed with the same or a new guessed action. Chat creation does not send text or media; the existing send command remains the sole DM path. The CLI `fanvue create-chat <accountId> --body-file <json> --idempotency-key <key>` calls the same route and requires explicit workspace binding.

`fanvue-read-client.ts` is an isolated, read-only provider transport. It requests chat messages with `markAsRead=false` and projects only stable IDs, message facts and media status; expiring media variant URLs are never returned through this layer. Offset chat/message/media results preserve Fanvue's `page`, `size` and `hasMore` metadata; v1 post/comment queries preserve opaque next cursors. Its callers must still enforce tenant/account reach and distinct module read grants before exposing any of these methods through browser or machine routes. The transport alone is not an enabled Fanvue engagement capability.

The provisional `FanvueReadService` is the account-scoped query owner for chats, messages, media status, posts and comments. It verifies an active Fanvue account joined to its active connection inside a tenant transaction, requires the corresponding provider read scope, then refreshes the server-held token and checks its effective scope again. The internal DM-send preflight additionally requires `write:chat` on the stored and refreshed grant and an exact fan counterpart in the selected creator's first chat message; an empty or mismatched chat is refused rather than claiming cold-DM authority. Machine routes require an explicit workspace header, separate `fanvue:chats:read`, `fanvue:posts:read` or `fanvue:media:read` key/delegated capabilities and rate limits. Authenticated browser routes use the same read service and projections under `content:read`, with no-store responses. The v1 post/comment lists preserve opaque next cursors; post collections expose only a 280-character preview while exact detail returns full text. Provider collection envelopes are capped at 50 rows and bounded text/media/cursor fields before any agent/browser serialization; an oversized or malformed provider response fails safely rather than becoming an unbounded API payload. These routes are not a complete engagement release until optional module re-consent and database-backed account-isolation tests are implemented and independently reviewed.

The initial publishing OAuth callback still exact-matches its requested scope set. Stored credential/refresh validation may retain only known additional `read:chat` while requiring every base publishing scope; it does not silently request that optional grant. The base now includes `read:post` and `read:media` for publishing readback/readiness. PostgreSQL fixture tests prove account/workspace denial, missing chat grant denial, and a deliberately seeded read-grant success path; they are not evidence of real Fanvue re-consent.

An explicit chat-read module re-consent starts from an active workspace-owned Fanvue account and binds that account ID into the encrypted one-use OAuth intent. The consent requests the full base publishing scope set plus only `read:chat`; no `write:chat` is included. At callback, the server consumes the intent, verifies the account remains active, exact-matches the returned scope set, and requires `/users/me` creator UUID to equal the selected account before replacing the subject-keyed credential. A wrong creator or missing chat scope cannot replace the prior grant. The module route remains a code-only backend boundary until a reviewed friendly account/module UI and Fanvue app allowed-scope plan make it usable; no live re-consent was exercised.

Fanvue is a distinct Core destination with a publishing-only base consent. `fanvue-http-client.ts` owns confidential-client Basic-auth authorization-code/PKCE transport and the pinned `2025-06-26` API version; the base requests `openid offline_access offline read:self read:media write:media read:post write:post`, never chat/comment scopes. The callback consumes the existing tenant/user-bound one-use OAuth state and encrypted verifier, requires an exact returned scope set, and discovers `/users/me` creator UUID before `connectProvider` atomically stores the encrypted token pair and subject-keyed account. Denial or failed validation cannot replace a prior grant. `fanvue-credential.service.ts` first locks the exact tenant/creator connection and commits a `refresh_pending` reconnect quarantine before presenting its single-use refresh token to Fanvue. A successful response atomically rotates the encrypted credential and restores that connection's active status; concurrent callers wait for this outcome without replaying the old token. Any provider ambiguity, process death, or failed post-call database commit leaves the old grant quarantined and requires reconnection. A lost refresh response cannot be safely replayed after Fanvue's grace window. Runtime routes and picker are enabled only when both Fanvue client environment keys are configured. This foundation alone does not authorize live OAuth or posting and never supplies provider tokens to agents.

`fanvue-webhook-signature.ts` verifies the documented `X-Fanvue-Signature` HMAC-SHA256 over timestamp, period and exact raw request bytes. It accepts rotation MACs against configured old/new secrets with constant-time comparison, rejects malformed or repeated timestamps and enforces a 300-second skew bound. The `X-Fanvue-Topic` header is not signed and cannot select a payment event or account. The eventual receiver must handle Fanvue's narrow unsigned subscription verification probe separately, verify all deliveries before parsing their signed bodies, durably dedupe/store mapped events before 2xx, and process asynchronously; this helper alone does not activate a webhook.

`fanvue-payment-event.ts` projects only signed `creator.payment.succeeded` facts: event and invoice IDs, creator/fan IDs, source, gross minor units/currency, paid/event timestamps, post/message UUIDs and tip context. It drops purchaser email, handle, tracking and unrelated metadata. A tip with `tip_context=message` is merely not-on-post, not proof of a chat origin or an offer match. The receiver must verify the raw signature before parsing and map the creator UUID to an authorized connected account before persisting or exposing any payment signal.

Review-first engagement approval uses the existing `engagement_proposals` row as the one-winner claim: the authenticated workspace owner/admin submits the exact revision with CSRF, the repository locks and rechecks the selected active account then changes `pending` to `sending` before any provider call. `engagement-approval.service.ts` invokes the same `FanvueCommentService.send` or `FanvueMessageService.sendText` command as direct-send agents, with the proposal's durable `clientActionId`; it supports text-only Fanvue comment/DM proposals for now. A proven pre-send permission, account, or target failure releases the claim to `pending` and returns actionable 409; original errors retain direct-command route mapping. Confirmed, definite provider failure and uncertain outcome settle to `sent`, `failed` and `unknown`; a lost settlement remains `sending` and must not be retried blindly. The review queue includes pending plus unresolved/failed outcomes after reload; sent and dismissed rows leave that queue. Media/price proposals and other providers remain non-sendable until their canonical commands are composed, not silently downgraded to text.
Optional Fanvue payment-signal consent uses `paymentAccountId` on the existing authenticated/CSRF-protected OAuth start route. It requests `read:creator` for that exact active creator while retaining the account's existing publishing/chat scopes; callback checks the same creator and all pre-existing plus requested scopes before replacing its credential. The account DTO exposes only a `paymentRead` boolean, separate from machine-key `fanvue:payments:read`; neither grants sending or activates a webhook subscription. The Developer Area allowed-scope superset and any live re-consent remain release-owner work.

## Accepted foundation

- Migration 0059 introduces `provider_account_exposures` as a stable workspace/account grant with nullable revocation and default-on `show_other_workspace_posts`. It backfills every origin self-exposure and creates self-exposure for future accounts; reconnect does not reactivate revoked target rows. `publication_jobs` now references the exposure pair rather than requiring the account's origin workspace, so a later authorized cross-workspace admission service can create target-owned jobs without copying the account or credential. This migration alone does not grant cross-workspace use: application admission and credential resolution must explicitly enforce an active exposure and origin/target ownership before enabling target selection.
- Provider-filtered scheduler claims join the active exposure pair to the canonical account ID; a revoked target exposure cannot yield a new Facebook dispatch. The Facebook worker reads Page identity from that canonical account, uses its origin workspace for credential lookup and availability updates, and keeps the creating workspace for job/media/artifact ownership. This is worker-side resolution only; browser admission remains a separate authorization boundary.
- `edit_facebook_page_exposure` is the narrow owner-only, `SECURITY DEFINER` mutation boundary for Facebook target grants. It requires the authenticated user to own both origin and target, locks origin then target workspace, rejects disconnected Pages, blocks revoke while target jobs are active or need reconciliation, retains the row on revoke, and writes only redacted origin-workspace audit metadata. `provider-account-exposure.service.ts` invokes it inside a tenant/user transaction; ordinary web SQL cannot directly grant a target exposure under forced RLS. Account discovery, browser API/UI and schedule admission consume this boundary in later slices.
- `PATCH /api/provider-accounts/:accountId/exposures/:workspaceId` is the browser checkbox mutation boundary. It requires workspace-management authorization and CSRF, accepts only `{ expose: boolean }`, delegates all cross-workspace authority and active-job checks to `editFacebookPageExposure`, and returns only the selected boolean. A missing/ineligible target is 404 and an active-job revoke is 409. The future checkbox UI must use a friendly workspace picker and discover current grants separately; this route does not accept raw IDs from a normal user form.
- `GET /api/provider-accounts/:accountId/exposures` is the checkbox-state read boundary. It requires workspace-management authorization and returns at most 100 active target workspace IDs plus a UUID cursor. Migration 0066 checks origin ownership and target ownership under a narrow definer projection, excludes tombstoned targets, and never returns credentials or unrelated grants. The browser combines this with the existing friendly workspace list; it must not display raw IDs.
- `provider_account_has_active_jobs` is the narrow origin-authorized `SECURITY DEFINER` disconnect guard. The account service calls it after locking the origin workspace, so queued/reconciliation-required jobs in any exposed workspace block revocation of the one credential. It returns only a boolean and does not broaden job or credential RLS; the older origin-only active-job query is retired.
- `resolve_exposed_post_accounts` is the narrow scheduling projection under forced RLS. Browser callers require target membership; machine callers retain their API-key or delegated-grant identity and the required schedule capability in transaction-local settings, checked against an active same-workspace credential rather than impersonating a human member. It returns only account/provider/capability metadata, never credentials or remote identity. Cross-workspace admission reserves origin workspace rows before target, rechecks active exposure and connection state in the same transaction, then writes the post and jobs in the target workspace. Only Facebook Pages may cross workspaces; X, Instagram and other providers retain origin-only admission. Read-only composer validation uses the same projection without row reservation. Meta grant and subject disconnect use the canonical account-wide active-job guard after the origin workspace lock, so jobs in exposed workspaces prevent credential revocation.
- `list_visible_exposed_facebook_pages_page` is the separate browser account-list projection for target members. It returns an allowlisted Page label, origin workspace name, availability/status and update time, not origin IDs, grant scopes, provider remote identity, defaults, or credential data. The authenticated account endpoint returns at most 100 summaries per page, ordered by provider/name/ID for local accounts then name/ID for exposed Pages. An opaque cursor advances the local or exposed keyset; the definer function enforces the exposed-page keyset and page bound before returning rows. Accounts and Composer explicitly load further pages without duplicating a Page or credential; mutating account commands still resolve only canonical origin-owned rows.
- The authenticated account endpoint supports server-side `provider=linkedin` filtering before its 100-row keyset page. The in-app LinkedIn expiry notice exhausts only that filtered collection, never relies on the first unfiltered account page; this preserves warnings when many other accounts precede LinkedIn in sort order.

- X long-post capability is a per-destination owner self-declaration, not provider verification: `provider_accounts.x_long_posts_allowed` defaults false and remains on the stable account row across reconnect. The tenant-scoped account summary exposes only `xLongPosts: { allowed, source: 'self_declared', verified: false }` for X (null otherwise). CSRF-protected `PATCH /api/provider-accounts/:accountId/x-long-posts` accepts only `{ allowed: boolean }` under `workspace:manage`, rejects non-X or disconnected accounts, and records actor/time through `audit_events`. The shared scheduling API honors this declaration; Composer reads the account summary and uses the same weighted X rule and selected-account limit, while mixed-provider selections retain their tighter safe constraint.

- Generic external clients create tenant-scoped imported drafts through `POST /api/v1/drafts` and inspect them through the principal-scoped detail route. Creation uses the canonical idempotency ledger and a separate actor/externalId replay identity. Draft media must already be ready and owned by the workspace. The authenticated cockpit reads the same draft under tenant RLS and atomically links it to exactly one canonical post during composer submission; no parallel scheduling or media lifecycle exists.

- Node.js 24 + strict TypeScript modular monolith using Fastify.
- PostgreSQL as the only durable state store.
- REST API for UI and project integrations.
- Provider adapters behind one explicit interface.
- Durable scheduled jobs with atomic claim/lease, idempotency, bounded retry/backoff, cancellation, reconciliation, and audit history.
- Scheduler persistence lives in `src/modules/scheduler`: claims use one `FOR UPDATE SKIP LOCKED` update, expired dispatch leases are marked reconciliation-required, and retry timing uses bounded full jitter. Stable publication idempotency derives only from job, immutable revision, and provider account identity.
- Cross-workspace worker claims use the distinct injected `WORKER_DATABASE_URL`, whose login receives only the `publish_relay_worker` group authority. That group has `BYPASSRLS`; the web login remains forced-RLS-bound and migration/ownership authority is never used by a runtime process. A PostgreSQL role administrator owns the one-time no-login-role creation and runtime membership grants; the database-owning migration login has `BYPASSRLS` for migrations/backups but never `CREATEROLE` or `CREATEDB`. All subsequent workspace-specific scheduler mutations establish `app.workspace_id` through `withTenantTransaction` before forced-RLS access.
- Secrets referenced through approved runtime/Vault mechanisms; never stored in plaintext project docs or logs.

- The application has one repository and build with separate `web` and `worker` process entrypoints. Production migrations execute the compiled `dist/database/migrate.js` entrypoint after a production-only dependency install; deployment never requires development-only `tsx`.
- `src/package-entrypoints/{application,runtime,auth}.ts` expose the narrow in-process Core composition contract; the build emits declarations for those package exports and the release artifact includes them plus the neutral policy contract. Hosted imports these entrypoints instead of copying Core implementation or reaching into private source paths. `registerCoreApplication` accepts a UI asset prefix for same-process Hosted composition, leaving the wrapper's `/` route intact while Core owns the public auth shells.
- `scripts/package-hosted-core.mjs` is the public-Core release artifact owner. From a clean, exact full Core commit it builds and packs the scoped `@21digital/publish-relay-core` identity with only the declared composition exports, emitted declarations, `dist`, and the complete source migration tree. It fresh-installs the tarball, imports all exported entrypoints, and byte-compares installed migrations before reporting its SHA-256 and source commit. `npm run package:hosted -- --output-dir DIR --expected-commit FULL_SHA` creates only an artifact; `--hosted-dir DIR --release-id ID` additionally advances a clean Hosted checkout to a NEW Core version by updating vendor, package dependency, manifest, and lock integrity. It refuses same-version replacement so an already reviewed release archive stays immutable. Hosted review/staging remains a separate release authority.
- Production releases are immutable directories under `/opt/publish-relay/releases` selected through an atomic `current` symlink. Separate hardened systemd web/worker units share one root-owned environment file. Deployments run forward migrations before switching the symlink; application rollback never reverses schema. Migration and authority-bootstrap commands inherit the release working directory from a parent subshell because the production sudo policy rejects `--chdir`/`-D`. Migration preserves only `DATABASE_URL` and `PGPASSWORD`; authority bootstrap passes the password-free migrator URL as `psql`'s explicit database argument and preserves only `PGPASSWORD`, preventing hardened sudo environment filtering from falling back to a local Unix socket. PostgreSQL backups use validated custom format, optionally encrypted with age, and capture never prunes existing archives. Restore drills fail closed unless the target differs from the production URL and database name and carries the `_restore` or `_restore_drill` suffix.
- Domain modules own their domain, application, and infrastructure internals. Cross-module imports use public contracts; another module's infrastructure is private and guarded by lint plus a regression test.
- Runtime input is validated with Zod. HTTP responses use `{ data, error }`. Pino logging is supplied through Fastify and must never include secrets or post bodies. Both standalone and caller-owned Hosted Fastify constructors must use Core's exported `requestLoggerOptions` so automatic request and error logs retain the method, path, client address, and request correlation while dropping the entire query string before serialization.
- Core also installs a path-only unmatched-route handler: Fastify's default 404 message otherwise interpolates the full query URL into log messages and responses. Keep this handler in same-process Hosted composition as well as standalone Core.
- For a definite X `POST /2/tweets` HTTP 403, the worker writes one server-side `x_post_denied` diagnostic to its service journal. The HTTP client allowlists only status, a bounded alphanumeric provider request/correlation ID, numeric error code, and exact known-safe title/detail phrases before invoking the sink. Unknown provider prose, response body, account identity, credentials, media URL and post text never enter that diagnostic or browser job detail. Diagnostic sink failure must not change the provider outcome.
- Vitest owns unit/integration tests and Playwright owns rendered browser acceptance.

Concrete architecture, security, persistence, job, and deployment decisions are frozen in `projects/publish-relay/library/decisions.md` ADR-001 through ADR-007.

## Core policy and commercial boundary

- `src/application/create-application.ts` is the public in-process composition seam. `registerCoreApplication` installs Core into a caller-owned Fastify instance from one typed options object; it does not create a second server or trust a remote identity header. `createStandaloneApplication` creates the normal Core-owned Fastify process and includes the public login, registration, and password-recovery shells. A composition may omit only those public shells; Core's auth/session API, protected application shell, authorization, provider routes, health, assets, and allow-all policy defaults remain Core-owned and unchanged. Registering Core twice on one Fastify instance is an error.
- Core's public `/login` route validates the same server-side session as `/app` before redirecting authenticated visitors to `/app`. It serves the public shell for absent, expired, or revoked sessions and marks this session-dependent response `no-store`.
- `src/application/create-runtime-options.ts` assembles the standalone database, storage, provider, and optional magic-link dependencies behind that composition seam. The web process still connects only with `publish_relay_web`; the worker alone uses its separate authority.
- `PUBLISH_RELAY_HUMAN_AUTH_MODE=magic_link` activates one email request contract for existing and first-time users. `MagicLinkService` owns neutral responses, bounded/rate-limited one-time challenges, same-origin redirect validation, and atomic verification; `magic-link.repository.ts` owns tenant-safe user/workspace/session persistence and clears a legacy password hash only after successful magic login. `auth-email-outbox.ts` stores encrypted pending delivery attached to each challenge, and the worker dispatches it through the Resend adapter. Production mode requires the pepper, Resend key, and sender address. Password endpoints return 404 in magic-link mode; a development URL may appear only outside production. Existing migrations 0040 and 0041 own the challenge/rate-limit/outbox tables; application schema declarations mirror those migrations.
- Magic links are bearer credentials: the 15-minute expiry and atomic single-use consume protect them, but verification does not bind to the requesting browser's user-agent because email clients commonly open links on another device. Emailed GET URLs for both verify paths render one shared no-store/no-referrer Continue page; GET and HEAD never inspect a challenge or mint a session. Its same-origin form sends the token in a bounded URL-encoded POST body, and only POST calls `MagicLinkService.verify`; the successful redirect contains no token. The page scrubs the query from browser history without automatically submitting. The reverse proxy must separately redact token-bearing request queries before a release. The standalone Fastify listener trusts forwarded client addresses only from its loopback reverse proxy, so network rate-limit buckets are per external client; a caller-owned Fastify composition must configure its own equivalent trusted-proxy boundary before enabling magic-link requests. `npm run test:e2e -- tests/e2e/magic-link.spec.ts` starts a magic-mode fixture directly; `npm run test:e2e:all` runs both password and magic suites.
- Core contains no commercial product concepts or schema. Never add Stripe, plans, prices, tier names, quota thresholds, marketing/storefront code, or Cloud-owned migrations.
- Commercially restrictable mutations call one injected neutral action-policy port from the command/application layer before mutation. The standalone implementation allows every commercial dimension; existing authentication, authorization, technical validation and provider safety constraints remain mandatory.
- Do not add an HTTP policy adapter without a later proven deployment requirement. The intended future private composition injects an in-process implementation that may participate in the same database transaction without Core importing private code.
- Policy inputs and denials use neutral facts and stable codes. UI routes, agent routes and CLI commands must not implement independent policy logic or bypass the application service.
- `src/modules/policy/action-policy.ts` owns the single `ActionPolicy` port, typed action names and decisions, neutral denial error, transaction-aware enforcement helper, and standalone allow-all implementation. Command services invoke it after technical validation but before any database, idempotency, storage, or provider mutation. Private composition may inject an in-process implementation through the application/service dependency boundary; Core does not call a remote policy service.
- X connect/reconnect admission occurs at OAuth initiation, before requesting a provider token or creating the encrypted request-token credential and OAuth transaction. The callback consumes that already-admitted transaction and must not evaluate policy a second time. API-key commands preserve the API-key actor plus request and idempotency identifiers through the shared service; browser commands preserve the user actor and the same request context. All HTTP boundaries map a denial to a stable safe 403 response.
- Core provides one authoritative workspace-scoped facts contract for retained bytes/media lifecycle, distinct provider families, connected provider accounts, publication targets, queued/scheduled targets and scheduling horizon. Future policy consumers do not duplicate queries.
- `getWorkspaceUsageFacts` in `src/modules/policy/usage-facts.ts` is that canonical transactional query. It runs under tenant context, counts retained bytes as every non-deleted media object, keeps requested targets distinct from persisted target facts, and is the only input future action-policy implementations should consume. Provider adapters own immutable `ProviderTechnicalCapabilities`; that metadata may describe verified technical shapes and numeric limits but never admission tiers or commercial policy.
- Provider capability metadata describes verified technical behavior and limits only. Provider adapters publish and reconcile; they never inspect commercial policy.
- Media byte deletion is Core lifecycle mechanics. Physical deletion is confirmed before tombstoning; audit identity/provenance remains; retained-byte facts exclude bytes actually deleted. Retention eligibility/deadline may be injected neutrally, but commercial durations never live in Core.
- `media-retention.service.ts` owns the tenant-scoped retention state machine. Core defaults to retain-forever; self-hosted composition may inject a neutral deadline policy (including the fixed-duration policy factory) without taking over eligibility checks or deletion. Evaluation excludes scheduled, leased, dispatching, retry-wait, accepted-pending, and reconciliation-required references. Cleanup claims are replay-safe, stale claims recover to retryable failure, storage success precedes the durable tombstone, and storage failure preserves retained-byte accounting plus retry ownership.

## Agent API v1 contract

Persistent macOS development uses `deploy/macos/publish-relay-local.sh`. It generates host-specific launchd plists and Vault-injected wrappers below the local state directory, runs isolated PostgreSQL on 55436 and web on 3106, preserves separate migration/web/worker authorities, and keeps runtime data outside source control.

- The dependency-light Node 24 CLI lives at `src/entrypoints/cli.ts`. It owns only named HTTP command mapping, secret-free profile/env loading, authenticated workspace routing, mutation workspace preflight, stable HTTP-to-exit mapping, compact JSON output, and bounded publication-job polling; it has no raw URL or database/provider passthrough. Every authenticated request sends the profile/`--require-workspace` value through `x-publish-relay-workspace`; mutations additionally verify the returned canonical account identity before writing.
- Every CLI success and error envelope crosses one recursive stdout allowlist. Only commands backed by live stable API DTOs are advertised: account current, posts create/list/show, publication-job show/poll, and health. Each authenticated command owns a response-key allowlist derived from its stable API DTO, so collection items/cursors, detail timestamps/states, and direct links remain machine-readable while unexpected nested fields are replaced with `[REDACTED]` before serialization.

- Shared success/error envelope builders and the signed keyset cursor codec live in `src/modules/api/contract.ts`; routes must use these canonical boundaries rather than hand-building response shapes or cursor parsing.
- Runtime Zod response schemas from that module are also the OpenAPI JSON Schema source; do not maintain a second handwritten schema for the same envelope.
- Collection cursors are versioned HMAC-SHA256 tokens bound to normalized filters and expiry. Malformed, tampered, expired, or filter-mismatched cursors fail closed and must map to HTTP 400 without restarting pagination.
- API admission uses the shared `ApiRateLimiter` with separate workspace and API-key buckets; mutation buckets are independently stricter, and rejected calls expose only bounded retry timing rather than tenant activity.
- Mutation request fingerprints use canonical JSON with sorted object keys while preserving array order; all mutation routes must validate a bounded `Idempotency-Key` before invoking the transactional replay store.
- `POST /api/v1/posts` is the canonical provider-neutral scheduling mutation. It requires `schedules:write`, mutation-rate admission, and `Idempotency-Key`; the API-key creator is the durable user attribution while the key remains the audit/idempotency principal. Its allowlisted response exposes only post/revision identity plus direct post and job links.
- `POST /api/v1/media` is the canonical agent media-ingest mutation. It requires `content:write`, mutation-rate admission, `Idempotency-Key`, `X-File-Name`, and exact local bytes. Images retain the 5 MiB ceiling. `video/mp4` has a neutral 2 GiB technical request ceiling and must pass byte-signature plus bounded `ffprobe` container/track inspection; Relay persists server-derived duration, dimensions, codecs, and container beside SHA-256 and byte size. The initial neutral video ceilings are 60 minutes and 8192 pixels per dimension. The byte/content-type fingerprint owns replay conflict detection; storage reuses the canonical media lifecycle. It never fetches remote URLs or trusts filename/client metadata.
- MP4 request bodies stream into a storage-owned temporary object while hashing, counting, enforcing the byte ceiling, and retaining only the signature prefix in memory. The completed file is probed in place, then atomically promoted to its canonical workspace/media/hash key inside idempotent persistence. Oversize, disconnect, probe failure, conflict, and replay paths delete the temporary object; a promoted object remains rollback-owned until the database transaction commits. Image callers retain the bounded `Buffer` storage path.
- Post mutation runtime and OpenAPI schemas share `src/modules/content/post.contract.ts`; the HTTP boundary and generated document must consume that contract rather than maintaining parallel request or response shapes.
- Provider-neutral post collection/detail and job detail reads use allowlisted projections from `post-read.repository.ts`. Post collections are capped at 100 rows and use `CursorCodec` cursors bound to the normalized collection filters; malformed or filter-mismatched cursors fail closed with 400.
- `GET /api/v1/jobs` uses the shared job-list tenant transaction, filters, ordering, and forced-RLS account resolver with a narrow machine projection; browser list/detail retain their richer projection. It requires `schedules:read`, caps pages at 100, orders by scheduled time then job ID descending, and binds signed cursors to normalized state, destination, date and limit filters. The query and response select only job ID/post ID, state, scheduled/updated timestamps and destination ID/display name/provider; response also adds detail links and next cursor. No content, credentials or cross-workspace aggregation. The shipped CLI exposes this as `publishes list` with matching filter flags.
- `CURSOR_SIGNING_SECRET` is required whenever database-backed API routes are registered and must contain at least 32 bytes of secret material supplied by runtime configuration.

## Persistence and tenant context

- Workspace picker ordering is membership-owned, not global workspace state: `memberships.position` stores each user's independent order. Authenticated workspace summaries sort by position, membership creation time, then workspace ID for deterministic legacy backfill behavior. Cross-workspace membership listing uses the fixed-search-path `list_user_workspaces` security-definer function, which requires `app.user_id` to match its argument and returns only the allowlisted summary contract.
- `POST /api/workspaces` creates a lightweight name-only workspace with the authenticated user as owner at the end of their list. `PATCH /api/workspaces/order` accepts one exact, duplicate-free permutation of every workspace visible to that user; repository writes re-establish tenant context for each membership. Switching workspaces also updates the user's default workspace while rotating only the current browser session.

- Drizzle schema declarations live in `src/database/schema.ts`; immutable forward migrations live in `migrations/`.
- Drizzle selects pending migrations by `when > max(created_at)`, not by journal index. Historical 0046/0047 LinkedIn entries have timestamps older than 0045 and must retain those values: 0.1.14 installations may have either applied or skipped them. Forward migration 0048 conditionally reconciles both schemas; future entries must use timestamps above the latest applied timestamp. Never retimestamp an issued journal entry to repair a partial installation.
- Tenant repositories require an explicit `workspaceId` and execute through `withTenantTransaction`, which applies transaction-local `app.workspace_id` before any tenant query.
- Tenant tables use both repository predicates and forced PostgreSQL RLS policies. Adding a tenant table requires `workspace_id`, indexes appropriate to its access path, and an RLS policy in the same migration.
- Browser session and API-key bearer material is never persisted. Store SHA-256 hashes; API keys expose only a public `pr_` prefix beside the hash. Revocation and expiry are checked before authorization.
- `src/modules/identity/api-key.ts` is the single agent-eligible capability registry. Authenticated browser Settings receives that registry from `GET /api/settings/api-keys` and selects every capability for a new key by default; the create request still supplies an explicit nonempty capability set, never an omitted implicit grant. Owner/admin Settings may replace an existing key's exact nonempty set through CSRF-protected `PATCH /api/settings/api-keys/:keyId` with `expectedVersion`. The tenant transaction conditionally advances `capability_version` and appends `api_key.capabilities_changed` with old/new capability names; stale or revoked edits return 409 and foreign keys remain 404. Secret, key ID, reach, and expiry do not change. Authentication reloads persisted capabilities on each request, so edits affect the next request; key-management/OAuth/workspace-management permissions are never in the registry.
- Browser session cookies carry the workspace UUID beside an opaque token so forced tenant RLS can be established before the hashed session lookup. Login rotates prior sessions, protected requests reload the live membership role, and state-changing browser routes require a matching double-submit CSRF token.
- Magic-link verification resolves the unscoped, single-use challenge and its user's default workspace under the challenge lock first, then sets transaction-local `app.workspace_id` before reading the forced-RLS membership. It fails closed if that membership is absent. Do not join `memberships` before setting tenant context: the production web role sees zero rows even for a valid link.
- The authenticated onboarding shell reloads its canonical workspace profile through `GET /api/workspaces/current`; profile changes use the matching CSRF-protected `PATCH` route and navigation uses the returned canonical slug.
- The protected shell identity comes from `GET /api/auth/session`, whose allowlisted detail DTO contains only the persisted user's display name/email and active membership workspace id/name/slug/role. It never exposes session material, hashes, default-workspace internals, or records from another tenant.
- A protected `/w/:slug/*` shell request compares the path slug with the authenticated session workspace resolved through the tenant-scoped workspace lookup. A mismatch redirects to the active workspace's canonical slug with the remaining path and query intact; it never switches sessions or serves a shell that could label active-tenant API data as another workspace. The existing CSRF-protected workspace switch endpoint is the only path for changing the active browser session.
- Audit events are append-only and accept allowlisted, redacted metadata only. Secrets and content bodies do not belong in audit or application logs.

A successful Instagram Login callback persists an active destination after exact-scope and eligible-account identity verification; the older Facebook Login Instagram destinations are made inert by migration 0057 without deleting jobs or changing Facebook Pages grants.

Provider adapters receive access tokens only in memory and return allowlisted account discovery DTOs. YouTube uses Google authorization-code PKCE with offline consent; the encrypted canonical credential contains the access token, refresh token, expiry, and granted scope, while connected-account discovery persists only channel IDs and display names.

Each workspace/member URN owns a distinct connection and credential; reconnect replaces only that member's credential without disconnecting other members. The connection row carries token expiry for truthful account status; no refresh is assumed. Dispatch reads tenant-owned jobs and credentials, refuses expired/mismatched members, records the REST `/rest/posts` receipt, retries definite HTTP 429 rejection with bounded backoff ([LinkedIn rate-limit contract](https://learn.microsoft.com/en-us/linkedin/shared/api-guide/concepts/rate-limits): rate-limited requests receive 429), and holds ambiguous 5xx/transport/missing-receipt outcomes for explicit reconciliation rather than posting twice. The codec rules are a safe member-feed subset, not a claim that ad-only features are supported. The same metadata is rechecked by the worker before upload.

An upload that crashes before its URN is durably recorded can orphan a provider asset but cannot create a post; never infer readiness from successful upload alone. Processing defers the leased job without creating a post attempt. Pre-POST upload/status network and provider-transient failures use the bounded LinkedIn retry policy and can never enter unknown-post reconciliation; validation/auth failures stop. A fresh owner-checked `AVAILABLE` read precedes the publication attempt and the Posts API rechecks readiness immediately before POST; only a possibly sent publication POST can enter ambiguous-outcome reconciliation.

The member Images API initializes and PUTs the image under `w_member_social`, stores the returned image URN in the existing job/media-bound provider-staging ledger, and reads readiness using the documented legacy **unversioned** `GET /rest/images/:urn` path. An Article may carry one optional tenant-owned image through the same ledger/readiness path; only the verified URN reaches `content.article.thumbnail`. The no-thumbnail Article path creates no image artifact. This is a fixture-tested contract; actual grant compatibility is reserved for the guarded live canary.

The legacy browser/agent post envelope permits up to 20 media IDs, but provider-specific admission retains tighter limits elsewhere. A possibly sent Posts API request retains the normal unknown-outcome/duplicate hold.

Refresh is triggered before expiry, writes through the credential repository's optimistic version guard, and reloads the winning encrypted credential when another process rotates first. ## Provider adapter contract

- Provider connection lifecycle and publication lifecycle are separate extension points. `ProviderConnectionDriver` owns connect/discover/revoke for an OAuth connection family; `PublishingAdapter` owns validate/stage/publish/lookup for one `destinationProvider`. Existing X and YouTube combined implementations retain the compatibility `ProviderAdapter` shape while new shared-family providers must keep the boundaries separate.
- `PublishingAdapterRegistry` selects behavior only by destination provider. The worker composes configured destination dispatch adapters through this registry, and scheduler claims plus dispatch/reconciliation context filter on `provider_accounts.destination_provider`, never the connection family. Generic content and scheduler modules must never infer an adapter from OAuth connection family, media type, or provider-specific imports.
- `provider_connections.external_subject_id` is the stable grant-principal key within workspace and provider. Migration 0051 preserves row and credential identities, backfills only proven single-destination X numeric IDs and LinkedIn member URNs, and gives YouTube/Meta and ambiguous X rows deterministic `legacy:<connection-id>` sentinels. New OAuth writes require X numeric `/2/users/me` ID, Google OIDC UserInfo `sub` (minimal `openid` renewal consent), Meta `debug_token.data.user_id`, LinkedIn member URN, or TikTok open ID. Reconnect matches only the exact subject; an overlapping destination owned by another grant or legacy row fails atomically for manual resolution, without account/job transfer or sibling credential mutation. The workspace connection write is serialized before conflict inspection. `provider-subject.service.ts` owns tenant-scoped version-CAS local refresh and subject disconnect; all nonterminal and reconciliation-required jobs block disconnect. The browser account API exposes account labels/IDs, not connection IDs; selected Meta remote-grant revoke resolves a workspace-owned account to its connection and revokes the whole grant, whereas ordinary account disconnect is local only. Callback errors without a verified existing connection never mark siblings unavailable. A zero-destination Meta family callback rejects before grant persistence; it disconnects and locally revokes only a matching active split-family grant proven to have zero provider accounts under the workspace lock, preserving valid prior and sibling grants.
- `src/modules/content/publication-target.ts` owns the versioned destination/content union for X, YouTube, Instagram, Facebook Pages, LinkedIn, and contract-only TikTok. The create/edit request and generated OpenAPI derive their explicit provider/content branches from that union; `normalizeCreatePostRequest` converts a validated target to the existing job command shape while retaining the legacy `providerAccountIds` request. A supplied destination is never reinterpreted as legacy, even if malformed or mixed with legacy fields. The selected provider is checked against the tenant-owned account's `destination_provider` before persistence, and no legacy request can schedule TikTok. Provider identity is never inferred from media.

## Content and media persistence

- Streamed uploads stage mode-0600 files under the local storage `.temporary` namespace. The worker reconciles this namespace on startup and every 60 seconds, removing only files older than `MEDIA_STAGING_STALE_MS` (24 hours by default); web startup performs the same idempotent sweep. Concurrent sweepers tolerate entries that disappear between enumeration and inspection, preserving fresh/in-flight uploads while deterministically bounding crash-orphan retention.

- `posts` owns mutable publication intent while `post_revisions` records immutable, numbered content snapshots. The database rejects revision update and deletion.
- Post and revision actor columns persist the authenticated user or named API key identity; `api_key` is identity while CLI is optional transport metadata only. Nullable actor columns are the explicit legacy/unknown state. Canonical job detail projections resolve safe actor labels and include ordered revision media, attempt/activity history, and the latest provider result.
- `publication_attempts.external_url` retains the validated HTTPS provider permalink with the successful attempt, including a resolved reconciliation. `providers/post-url.ts` owns host validation and conservative historical ID-derived links: Facebook Page, X (with handle), YouTube, and LinkedIn may derive a URL; Instagram requires an actual permalink. Job detail projects only the latest published attempt's ID and safe URL, and never invents a link for failed or unknown outcomes. The browser uses the existing provider-result affordance for every provider.
- `revision_media` links ordered workspace media to a revision. `publication_jobs` creates one independent account target per revision, and `provider_staging_artifacts` records temporary provider-side resources that require deterministic cleanup.
- `validateTargetOwnership` is the shared create/edit admission boundary for X text length across browser, API, and CLI. It resolves every selected workspace-owned destination and its persisted `x_long_posts_allowed` flag in the tenant transaction; `x-text-length.ts` uses the official `twitter-text` weighted count on the actual dispatch text: each part of a media-backed object thread, or the trimmed, double-newline-joined text of a media-free or string-part thread. The composition helper is shared with dispatch. Undeclared accounts cap at 280, self-declared accounts at 25,000, and a mixed X selection obeys the tightest account. The destination-first X contract preserves canonical `posts` thread parts. Client-provided entitlement is never accepted. Schedule-only rescheduling still checks account/media ownership and connection state, but preserves an already-admitted revision without reapplying a later-changed X length declaration. Stored revisions are not revalidated at dispatch.
- `POST /api/v1/posts/validate` is a schedules:read, read-rate-limited technical preview of the create request shape. It reuses target ownership, media, X weighted-length, and provider-settings checks in a read-only tenant transaction, returns bounded per-destination validity and X weighted length/limit, and makes no post/job/media/audit write. For an X object-thread with no uploaded media IDs, the validation-only `validationPreview: { "xMediaPresent": true }` applies per-part length admission and returns `mediaNotValidated: true`; this cannot check future media ownership or content. Other provider/content shapes and already-attached media are rejected for this mode. A preview is not a reservation; create remains authoritative after upload and may reject after state changes.
- The `publish-relay posts validate --body-file candidate.json --require-workspace <workspace-id>` CLI command accepts that same preview-only field and exposes `mediaNotValidated`; `posts create` does not accept the preview field as an admission override.
- The worker's bounded provider-staging cleanup cycle is provider-aware. Instagram artifact rows remain live while their job is active or reconciliation-required, then stay as restart/audit evidence for a full 24-hour terminal grace after `published`, `failed`, `cancelled`, or `superseded`. Only expired Instagram artifacts whose terminal grace has elapsed are tombstoned; their local artifact keys are never passed to a generic external-object deletion adapter.
- Every content/media table is workspace-scoped with explicit repository predicates and forced RLS. Media identity records a storage key plus byte-derived SHA-256, MIME type, and byte size; application services must not trust client metadata for those fields.
- The durable worker runs bounded media-retention cycles across workspaces. `MEDIA_RETENTION_DAYS` is an optional neutral self-hosted policy (omission retains forever); cadence, retry, stale-claim recovery and batch size are operator configuration. Revision creation locks referenced media and revives eligible/failed retained bytes, while cleanup locks candidates and atomically rechecks active job references before physical deletion.

  Transient polling retries default to five seconds and provider `Retry-After` is bounded to five

`fanvue_payment_subscriptions` (migration 0082) is the per-creator callback owner, separate from app-wide Fanvue Events/Manifest routing. The tenant/account-bound repository checks the selected active Fanvue creator plus `read:self` and `read:creator` before reserving a random one-use callback handle; only its SHA-256 hash is stored. A provider creation attempt moves `probe_pending` to `creation_unknown` before external mutation, so a lost response cannot be blindly retried; the callback remains probe-capable in both states (migration 0084). An unused `probe_pending` reservation can be cancelled without a provider call. `creation_unknown` remains open on an empty provider list because the original POST may still complete; release requires discovery and confirmed deletion of its exact matching provider destination. A confirmed create locks and rechecks the selected active account/creator/payment consent before atomically storing the provider ID and envelope-encrypted returned-once signing secret, then marks `active`. If consent was revoked before that locked check, migration 0085 permits `deletion_required`: persist only the confirmed provider ID, never the signing secret, so exact provider deletion remains possible. Only a confirmed matching provider deletion marks an `active` or `deletion_required` row `disabled` and revokes any signing credential. The row survives as history; a new account subscription can then reserve a new handle. Provider create/delete transport and gap reconciliation remain separate slices, not implicit effects of these repository calls.

`resolve_fanvue_payment_callback` (migrations 0083–0084) is the narrow `SECURITY DEFINER` cross-tenant handle lookup, executable only by the web role. It accepts the hash of a structurally valid opaque handle and projects only the selected workspace/account/creator, state and secret credential reference for an active, probe-pending or creation-unknown subscription whose Fanvue connection and payment scope remain active. `resolveFanvuePaymentCallback` rechecks the active row, account and connection under tenant RLS before decrypting the selected signing credential, and returns either probe-pending or the account-bound signed-delivery input. Disabled/revoked/unknown handles return no mapping. The resolver is not a public account-discovery API; callback responses/logs never expose these IDs or plaintext secrets. The isolated JSON raw-body parser applies only to `POST /webhooks/fanvue/payments/:handle`: it answers the exact unsigned `fanvue.webhook.verification` body for a probe-capable handle, sends active deliveries through signature-before-parse and durable payment receipt, and returns 2xx on payment only after that receipt. Provider subscription create/delete transport and gap reconciliation remain separate acceptance.
The callback path also carries a bearer handle. `requestPath` in the shared request logger redacts the full `/webhooks/fanvue/payments/...` suffix for normal request/error logs and unmatched-route response bodies; route resolution still receives the real handle. Keep this redaction in step with any future callback path change.

`FanvuePaymentSubscriptionClient` is only the provider transport for the documented creator-token `POST` and `DELETE /webhooks/subscriptions` API. Create requests exactly `creator.payment.succeeded` and returns the one-time signing secret to its caller; it neither stores the secret nor decides consent or retries. An HTTP 4xx create denial is definite, whereas transport failure, HTTP 5xx or malformed success leaves creation outcome unknown. Delete accepts a confirmed success or provider 404 as absence; transport failure remains unknown. The tenant subscription repository and a future account-scoped command own durable pre-call intent, activation and provider-backed reconciliation. Do not call this transport directly from a browser route or treat it as live activation.
The read-only provider list transport accepts bounded documented subscription fields in a direct array or explicit `data`/`subscriptions` envelope, and fails closed on every other shape; this response envelope must be confirmed against a controlled provider fixture before live activation. `reconcileFanvuePaymentCreation` compares only callback URLs on the configured HTTPS Relay origin whose exact 43-character handle hashes to the tenant-owned pending row. An empty list leaves `creation_unknown` pending: a timed-out create POST may still finish after the list. Only after an exact matching provider destination is found, its provider ID is confirmed deleted, and a second list shows it absent does reconciliation release the row. A list, delete or second-list failure leaves the row open; neither a loose URL prefix nor a local timeout is proof of absence.
The internal `createFanvuePaymentSubscription` command reserves the selected account before using its creator token, lists for existing Relay callbacks before another create, cancels only an unused reservation on preflight failure, marks the create intent before the outbound POST, and activates only after the returned ID/one-time secret are durably stored. If the pre-POST mark throws, it reads durable state: an unchanged `probe_pending` row can be cancelled because no provider call began; `creation_unknown` or an unreadable state stays open because commit acknowledgement may have been lost. An uncertain POST or persistence error likewise leaves the row open for reconciliation. The internal delete command verifies exact selected creator and confirmed provider ID, deletes remotely first, then disables locally; remote failure leaves local state open. Neither command is exposed in a browser or agent route yet. Live activation, operator-facing management control and controlled provider response-shape proof are separate release acceptance.

It does not expose storage keys, hashes, credentials, source actor/client IDs, or arbitrary media metadata. Missing media metadata remains explicit rather than inferred from attachment count; Composer removal is local selection, not a mutation of the source draft.

- `external_drafts` is the durable tenant-scoped handoff aggregate for authorized external applications. ## Delegated client authorization

- `src/modules/delegated-authorization/protocol.ts` is the provider-neutral protocol boundary for registered clients. Authorization requests require a non-empty client state, exact redirect-URI allowlisting, PKCE S256, and a non-empty subset of the client's registered scopes.
- Authorization codes, access tokens, refresh tokens, and confidential-client secrets are opaque random values. Durable storage receives only SHA-256 hashes; comparison uses constant-time equality. Codes expire after five minutes and access tokens after fifteen minutes unless a later owner-approved contract changes those named constants.
- Registered clients are environment-owned configuration/data rather than schema or route owners. Grant lifecycle, exchange, rotation, revocation, and audit behavior remain generic Relay responsibilities. Wildcard, arbitrary-port, and client-supplied callback registration are forbidden.
- `registered_clients` owns global client identity and exact redirect/scope allowlists. `delegated_grants` owns one active user-approved client connection per workspace; a revoked grant remains as history and reconnect creates a new grant without touching unrelated API keys.
- `delegated_authorization_codes` and `delegated_tokens` are grant-owned, workspace-scoped credential ledgers protected by forced RLS. Hash uniqueness is global, authorization codes are single-use through `consumed_at`, refresh rotation links the replacement to its predecessor, and grant revocation invalidates every descendant credential.
- `DelegatedAuthorizationService` is the protocol orchestration boundary. It validates registered clients before approval, passes only hashes and the derived PKCE challenge to persistence, and requires atomic store operations for code verification/token issuance and refresh rotation. HTTP routes and API authentication must call this service rather than reproducing PKCE, expiry, hashing, or rotation rules.
- Delegated clients use the existing `/api/v1` resource contract with `Authorization: Bearer <access-token>` and the explicit `X-Publish-Relay-Workspace` preflight. Capability guards, action policy, idempotency, audit attribution, rate limits, and tenant hiding are shared with API keys; clients must not infer a separate delegated API surface. Clients verify callback state, exchange codes server-side, encrypt token responses at rest, rotate refresh tokens, and treat Relay-side grant revocation as terminal reauthorization.
- Authenticated `GET /api/v1/account` is the canonical machine connection receipt. API-key output remains unchanged; delegated bearer output allowlists only `principalType=delegated`, client/grant/workspace identity and label, granted capabilities, and access-token expiry. The resolver derives that receipt from active token/grant/workspace rows without exposing user identity or token material, and the response is never cached.
- `src/modules/delegated-authorization/delegated-authorization.routes.ts` is the generic HTTP boundary. Browser navigation to `/connect/authorize` serves the authenticated consent shell or redirects to login with a same-origin continuation; JSON negotiation on the same URL validates the registered client before presenting consent. Approval binds to the authenticated session workspace/user, requires CSRF, and returns either the protocol redirect or a JSON redirect instruction for the SPA. `/connect/token` accepts only authorization-code or refresh-token grants and emits stable OAuth-style error fields with `Cache-Control: no-store`; callback redirects contain only the short-lived authorization code and exact client state. `POST /connect/revoke` accepts a client's own access or refresh token plus client ID (and the registered secret for confidential clients), atomically revokes that grant family, and returns an opaque idempotent empty 200 for unknown/already-revoked tokens; all responses are `no-store`. `GET /api/settings/delegated-grants` returns at most 100 active grants owned by the authenticated workspace/user, projected to grant ID, client ID, scopes, and creation time; token material, internal ownership fields, and revoked history are absent. User revocation is a CSRF-protected, tenant-bound settings mutation and never touches unrelated API keys.
- Opaque delegated credentials resolve through three narrowly granted `SECURITY DEFINER` database functions with a fixed search path. They accept hashes (plus the derived PKCE challenge for exchange), return the minimum grant principal, preserve forced tenant RLS on all tables, and own the atomic verify-consume-issue/access-touch/refresh-rotation mutations. Function privileges belong only to the canonical `publish_relay_web` authority and are applied by database bootstrap after roles exist; migrations must remain fresh-install safe when fixed roles have not been created yet. Application SQL must never disable RLS or accept a caller-supplied workspace as credential authority.
- `createPostgresDelegatedAuthorizationStore` is the only application adapter for delegated grant/code/token persistence. Tenant-known mutations use the canonical tenant transaction; opaque credential resolution calls only the audited hash-based functions above.
- Grant approval and revocation write `delegated_grant.approved` and `delegated_grant.revoked` audit events in the same tenant transaction as the lifecycle mutation. The authenticated user is the actor, the grant is the target, request correlation is retained, and approval metadata contains only client ID and approved scopes.

`GET /api/v1/destinations` is the canonical account-scoped discovery surface for API customers. It requires `destinations:read`, returns at most 100 summaries per response with an opaque `nextCursor` (null at the end), and accepts that cursor as an optional query parameter; invalid cursors return 400. The CLI exposes `destinations list --cursor <nextCursor>` for subsequent pages. It returns only the provider-account ID, connection family, destination provider, display name, connection status, availability, remote parent identity where useful, the bounded capability snapshot/freshness, and timestamps. Credential IDs, connection IDs, provider metadata, defaults, ownership fields, and secret material are never exposed by this collection contract.

Machine destination discovery passes the authenticated actor type, ID, and `destinations:read` through the tenant transaction. The shared paginated account listing combines local accounts with the existing exposed Facebook Page projection; migration 0075 admits only active target-workspace API keys or delegated grants with that capability, alongside the existing browser-member path. It does not impersonate a member or widen foreign account RLS. The API continues to serialize the same allowlisted summary for both local and exposed destinations, without origin workspace or credential fields.

`POST /api/v1/jobs/:jobId/retry` is the canonical agent retry surface. It requires `publishes:retry`, an idempotency key, and a tenant-owned failed job whose outcome does not require reconciliation. The API-key identity is retained as the policy and event actor; unknown outcomes must be reconciled rather than blindly retried.

Provider runtime registration is isolated: missing provider-specific credentials disable only that provider and emit a secret-free `provider_disabled` event. Common worker prerequisites may still fail startup, but one provider's absent configuration must not prevent unrelated providers or retention/reconciliation infrastructure from running.

# Browser create response

Production releases install production dependencies without building on the host, then restore the reviewed compiled `dist` artifact from the release source before migration and validation. The complete release tree is normalized to deploy-owner plus service-group ownership with owner read/write/traverse, service-group read/traverse, and no access for other users; deployment fails before migration unless the service user can read the compiled migration entrypoint. Readiness is probed only after both systemd units restart. The canonical release script uses a bounded configurable retry window (12 attempts, two seconds apart by default), retains curl's fail-closed behavior, and exits nonzero after exhaustion. The shared lifecycle restores and verifies the prior application before deleting a failed candidate, or preserves both artifacts when recovery cannot be proven.

## Release artifact lifecycle

- `deploy/publish-release.sh` and rebuilt-source `rollback-release.sh` converge on `release-lifecycle.sh`: one release normally, a temporary candidate second, then one after verified success or successful recovery. A sibling exclusive directory lock spans the transaction; failed recovery or cleanup preserves it for owner reconciliation.
- `deploy/release-filesystem.mjs` owns canonical-root validation, protected-path checks, safe contained symlinks, migration-tree comparison, exact `current` and MainPID working-directory verification, and open-file checks before bounded removal. No live database, media, or backup is deleted. Migration changes, extra legacy releases, stale observations, and unknown process state refuse rather than guessing. Full activation and recovery boundaries live in `deploy/RELEASE-RETENTION.md`.

- Browser post creation returns bounded job summaries containing only job ID and persisted `effectiveProviderSettings`, so clients can retain the resolved destination-default snapshot without reconstructing it.
- Browser Composer uploads remain unattached until post creation succeeds. Its authenticated CSRF-protected media delete endpoint atomically tombstones only tenant-owned ready media with no revision reference, then removes the local object; attached media is never deleted through this abandonment path.
- Browser image uploads honor provider technical limits: JPEG/PNG/WebP at 5 MiB and GIF at 15 MiB for X. Composer reuses uploaded media IDs only for the exact selected `File` objects; a same-count replacement requires cleanup and a fresh media-upload batch key. After an uncertain post response, it freezes the exact serialized request, post key, form and file selection, and replays only that immutable request until the server confirms the outcome. Confirmed cleanup rotates the media-upload key; changed input must never replay old media IDs under a new post key.

## Review-first engagement proposals (foundation)

- `engagement_proposals` is the provider-neutral, workspace/account-bound queue for optional DM/comment review. Its client action ID is unique per workspace, and source context plus proposed content are durable snapshots. `src/modules/providers/engagement-proposal.repository.ts` owns idempotent create, pending list, optimistic edit, and dismiss; a stale edit cannot overwrite another reviewer's revision.
- The proposal row is not a provider send ledger. Approve/send must recheck the connected account and current capability, reserve one action, then call the same canonical DM/comment command as direct-send agents. `approved`, `sending`, `sent`, `unknown`, and `failed` states are reserved for that later command integration; do not mark them through proposal CRUD or infer that a pending row was sent.
- The proposal API is split by actor: `POST /api/v1/engagement-proposals` requires a machine `engagement:propose` capability and an explicit workspace header; browser create, list, detail, edit and dismiss under `/api/engagement-proposals` require authenticated workspace content permissions, with CSRF on mutations. Both paths call the same workspace-bound repository. Input fields and pending-list output are bounded; the list is keyset-paginated at 50 small preview rows, while exact source/proposed text is available only through workspace-authorized detail. Provider tokens and full account records are never serialized. These endpoints stage review data only and cannot send to a provider.
- SQL enforces same-workspace account foreign keys and tenant RLS. Proposal creation checks exact active account/connection reach; provider media readiness, price validity and send capability must still be rechecked by the later canonical approve/send command. This foundation performs no provider call.

For new actions it locks both the selected account and its active, unrevoked connection before insert; concurrent disconnect/revoke must serialize behind that admission. Tenant RLS is forced even for the table owner.
