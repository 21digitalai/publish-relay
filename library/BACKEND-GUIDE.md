# Publish Relay Backend Guide

## Accepted foundation

- Generic external clients create tenant-scoped imported drafts through `POST /api/v1/drafts` and inspect them through the principal-scoped detail route. Creation uses the canonical idempotency ledger and a separate actor/externalId replay identity. Draft media must already be ready and owned by the workspace. The authenticated cockpit reads the same draft under tenant RLS and atomically links it to exactly one canonical post during composer submission; no parallel scheduling or media lifecycle exists.

- Node.js 24 + strict TypeScript modular monolith using Fastify.
- PostgreSQL as the only durable state store.
- REST API for UI and project integrations.
- Provider adapters behind one explicit interface.
- Durable scheduled jobs with atomic claim/lease, idempotency, bounded retry/backoff, cancellation, reconciliation, and audit history.
- Scheduler persistence lives in `src/modules/scheduler`: claims use one `FOR UPDATE SKIP LOCKED` update, expired dispatch leases are marked reconciliation-required, and retry timing uses bounded full jitter. Stable publication idempotency derives only from job, immutable revision, and provider account identity.
- Cross-workspace worker claims use the distinct injected `WORKER_DATABASE_URL`, whose login receives only the `publish_relay_worker` group authority. That group alone has `BYPASSRLS`; the web login remains forced-RLS-bound and migration/ownership authority is never used by a runtime process. All subsequent workspace-specific scheduler mutations establish `app.workspace_id` through `withTenantTransaction` before forced-RLS access.
- Secrets referenced through approved runtime/Vault mechanisms; never stored in plaintext project docs or logs.

- The application has one repository and build with separate `web` and `worker` process entrypoints. Production migrations execute the compiled `dist/database/migrate.js` entrypoint after a production-only dependency install; deployment never requires development-only `tsx`.
- Production releases are immutable directories under `/opt/publish-relay/releases` selected through an atomic `current` symlink. Separate hardened systemd web/worker units share one root-owned environment file. Deployments run forward migrations before switching the symlink; application rollback never reverses schema. Migration and authority-bootstrap commands inherit the release working directory from a parent subshell because the production sudo policy rejects `--chdir`/`-D`. Migration preserves only `DATABASE_URL` and `PGPASSWORD`; authority bootstrap passes the password-free migrator URL as `psql`'s explicit database argument and preserves only `PGPASSWORD`, preventing hardened sudo environment filtering from falling back to a local Unix socket. PostgreSQL backups use custom format encrypted with age. Restore drills fail closed unless the target differs from the production URL and database name and carries the `_restore` or `_restore_drill` suffix.
- Domain modules own their domain, application, and infrastructure internals. Cross-module imports use public contracts; another module's infrastructure is private and guarded by lint plus a regression test.
- Runtime input is validated with Zod. HTTP responses use `{ data, error }`. Pino logging is supplied through Fastify and must never include secrets or post bodies.
- Vitest owns unit/integration tests and Playwright owns rendered browser acceptance.

Concrete architecture, security, persistence, job, and deployment decisions are frozen in `projects/publish-relay/library/decisions.md` ADR-001 through ADR-007.

## Core policy and commercial boundary

- Core contains no commercial product concepts or schema. Never add Stripe, plans, prices, tier names, quota thresholds, marketing/storefront code, or Cloud-owned migrations.
- Commercially restrictable mutations call one injected neutral action-policy port from the command/application layer before mutation. The standalone implementation allows every commercial dimension; existing authentication, authorization, technical validation and provider safety constraints remain mandatory.
- Do not add an HTTP policy adapter without a later proven deployment requirement. The intended future private composition injects an in-process implementation that may participate in the same database transaction without Core importing private code.
- Policy inputs and denials use neutral facts and stable codes. UI routes, agent routes and CLI commands must not implement independent policy logic or bypass the application service.
- `src/modules/policy/action-policy.ts` owns the single `ActionPolicy` port, typed action names and decisions, neutral denial error, transaction-aware enforcement helper, and standalone allow-all implementation. Command services invoke it after technical validation but before any database, idempotency, storage, or provider mutation. Private composition may inject an in-process implementation through the application/service dependency boundary; Core does not call a remote policy service.
- X connect/reconnect admission occurs at OAuth initiation, before requesting a provider token or creating the encrypted request-token credential and OAuth transaction. The callback consumes that already-admitted transaction and must not evaluate policy a second time. API-key commands preserve the API-key actor plus request and idempotency identifiers through the shared service; browser commands preserve the user actor and the same request context. All HTTP boundaries map a denial to a stable safe 403 response.
- Core provides one authoritative workspace-scoped facts contract for retained bytes/media lifecycle, distinct provider families, connected provider accounts, publication targets, queued/scheduled targets and scheduling horizon. Future policy consumers do not duplicate queries.
- `getWorkspaceUsageFacts` in `src/modules/policy/usage-facts.ts` is that canonical transactional query. It runs under tenant context, counts retained bytes as every non-deleted media object, keeps requested targets distinct from persisted target facts, and is the only input future action-policy implementations should consume. Provider adapters own immutable `ProviderTechnicalCapabilities`; that metadata may describe verified technical shapes and numeric limits but never admission tiers or commercial policy.
- Provider capability metadata describes verified technical behavior and limits only. Provider adapters publish and reconcile; they never inspect commercial policy.
- Media byte deletion is Core lifecycle mechanics. Physical deletion is confirmed before tombstoning; audit identity/provenance remains; retained-byte facts exclude bytes actually deleted. Retention eligibility/deadline may be injected neutrally, but commercial durations never live in Core.
- `media-retention.service.ts` owns the tenant-scoped retention state machine. Core defaults to retain-forever; self-hosted composition may inject a neutral deadline policy (including the fixed-duration policy factory) without taking over eligibility checks or deletion. Evaluation excludes scheduled, leased, dispatching, retry-wait, accepted-pending, and reconciliation-required references. Cleanup claims are replay-safe, stale claims recover to retryable failure, storage success precedes the durable tombstone, and storage failure preserves retained-byte accounting plus retry ownership.

## Agent API v1 contract

Persistent macOS development uses `deploy/macos/publish-relay-local.sh`. It generates host-specific launchd plists and Vault-injected wrappers below the local state directory, runs isolated PostgreSQL on 55436 and web on 3106, preserves separate migration/web/worker authorities, and keeps runtime data outside source control.

- The dependency-light Node 24 CLI lives at `src/entrypoints/cli.ts`. It owns only named HTTP command mapping, secret-free profile/env loading, authenticated workspace routing, mutation workspace preflight, stable HTTP-to-exit mapping, compact JSON output, and bounded publication-job polling; it has no raw URL or database/provider passthrough. Every authenticated request sends the profile/`--require-workspace` value through `x-publish-relay-workspace`; mutations additionally verify the returned canonical account identity before writing.
- Every CLI success and error envelope crosses one recursive stdout allowlist. Only commands backed by live stable API DTOs are advertised: account current, posts create/list/show, publication-job show/poll, and health. Each authenticated command owns a response-key allowlist derived from its stable API DTO, so collection items/cursors, detail timestamps/states, and direct links remain machine-readable while unexpected nested fields are replaced with `[REDACTED]` before serialization.

- Shared success/error envelope builders and the signed keyset cursor codec live in `src/modules/api/contract.ts`; routes must use these canonical boundaries rather than hand-building response shapes or cursor parsing.
- Runtime Zod response schemas from that module are also the OpenAPI JSON Schema source; do not maintain a second handwritten schema for the same envelope.
- Collection cursors are versioned HMAC-SHA256 tokens bound to normalized filters and expiry. Malformed, tampered, expired, or filter-mismatched cursors fail closed and must map to HTTP 400 without restarting pagination.
- API admission uses the shared `ApiRateLimiter` with separate workspace and API-key buckets; mutation buckets are independently stricter, and rejected calls expose only bounded retry timing rather than tenant activity.
- Mutation request fingerprints use canonical JSON with sorted object keys while preserving array order; all mutation routes must validate a bounded `Idempotency-Key` before invoking the transactional replay store.
- `POST /api/v1/posts` is the canonical provider-neutral scheduling mutation. It requires `schedules:write`, mutation-rate admission, and `Idempotency-Key`; the API-key creator is the durable user attribution while the key remains the audit/idempotency principal. Its allowlisted response exposes only post/revision identity plus direct post and job links.
- `POST /api/v1/media` is the canonical agent media-ingest mutation. It requires `content:write`, mutation-rate admission, `Idempotency-Key`, `X-File-Name`, and exact local bytes. Images retain the 5 MiB ceiling. `video/mp4` has a neutral 2 GiB technical request ceiling and must pass byte-signature plus bounded `ffprobe` container/track inspection; Relay persists server-derived duration, dimensions, codecs, and container beside SHA-256 and byte size. The initial neutral video ceilings are 60 minutes and 8192 pixels per dimension. The byte/content-type fingerprint owns replay conflict detection; storage reuses the canonical media lifecycle. It never fetches remote URLs or trusts filename/client metadata.
- MP4 request bodies stream into a storage-owned temporary object while hashing, counting, enforcing the byte ceiling, and retaining only the signature prefix in memory. The completed file is probed in place, then atomically promoted to its canonical workspace/media/hash key inside idempotent persistence. Oversize, disconnect, probe failure, conflict, and replay paths delete the temporary object; a promoted object remains rollback-owned until the database transaction commits. Image callers retain the bounded `Buffer` storage path.
- Post mutation runtime and OpenAPI schemas share `src/modules/content/post.contract.ts`; the HTTP boundary and generated document must consume that contract rather than maintaining parallel request or response shapes.
- Provider-neutral post collection/detail and job detail reads use allowlisted projections from `post-read.repository.ts`. Post collections are capped at 100 rows and use `CursorCodec` cursors bound to the normalized collection filters; malformed or filter-mismatched cursors fail closed with 400.
- `CURSOR_SIGNING_SECRET` is required whenever database-backed API routes are registered and must contain at least 32 bytes of secret material supplied by runtime configuration.

## Persistence and tenant context

- Drizzle schema declarations live in `src/database/schema.ts`; immutable forward migrations live in `migrations/`.
- Tenant repositories require an explicit `workspaceId` and execute through `withTenantTransaction`, which applies transaction-local `app.workspace_id` before any tenant query.
- Tenant tables use both repository predicates and forced PostgreSQL RLS policies. Adding a tenant table requires `workspace_id`, indexes appropriate to its access path, and an RLS policy in the same migration.
- Browser session and API-key bearer material is never persisted. Store SHA-256 hashes; API keys expose only a public `pr_` prefix beside the hash. Revocation and expiry are checked before authorization.
- Human browser authentication uses identity-owned one-time challenges, never API keys or provider OAuth transactions. Raw tokens and normalized email/network identifiers are never persisted: store token hashes and dedicated-pepper HMAC keys, consume with one atomic unexpired/unconsumed database predicate, and return the same 202/failure envelopes for absent, limited, expired, replayed, and mismatched accounts. Challenges expire after 15 minutes and persist only validated relative redirects (default `/app`). Shared PostgreSQL rate-limit buckets survive multiple processes and restarts. `PUBLISH_RELAY_HUMAN_AUTH_MODE=password|magic_link` defaults to password for the expand/compatibility release; existing sessions and nullable legacy password hashes remain valid. Hosted magic-link mode fails startup without Resend configuration, a verified sender, HTTPS public origin, and challenge pepper; development alone may expose the one-time URL.
- Magic-link request, suppression, delivery, and verification outcomes emit bounded in-process Prometheus counters. Labels are a fixed allowlist of lifecycle states; email addresses, tokens, IP/network identifiers, correlation IDs, and provider response bodies never enter metric names or labels.
- Hosted magic-link delivery enqueues one envelope-encrypted identity-owned outbox row per challenge. The durable worker claims rows with bounded leases and `SKIP LOCKED`, decrypts only in memory, uses the challenge correlation ID as the provider idempotency key, records only a fixed redacted failure code, and retries with bounded exponential delay. A challenge becomes verifiable only after the provider send succeeds and the worker atomically records its provider message ID and `sent` delivery state.
- Browser session cookies carry the workspace UUID beside an opaque token so forced tenant RLS can be established before the hashed session lookup. Login rotates prior sessions, protected requests reload the live membership role, and state-changing browser routes require a matching double-submit CSRF token.
- The authenticated onboarding shell reloads its canonical workspace profile through `GET /api/workspaces/current`; profile changes use the matching CSRF-protected `PATCH` route and navigation uses the returned canonical slug.
- The protected shell identity comes from `GET /api/auth/session`, whose allowlisted detail DTO contains only the persisted user's display name/email and active membership workspace id/name/slug/role. It never exposes session material, hashes, default-workspace internals, or records from another tenant.
- Audit events are append-only and accept allowlisted, redacted metadata only. Secrets and content bodies do not belong in audit or application logs.

## Provider credentials and OAuth

- Provider secrets use AES-256-GCM envelope encryption: a random data key encrypts each record and a versioned master key wraps only that data key. Rotation uses optimistic record versions and never rewrites plaintext.
- Credential, provider connection/account, and OAuth transaction rows are workspace-scoped tenant tables with forced RLS. Repository calls run inside `withTenantTransaction` and repeat the workspace predicate.
- OAuth state is persisted only as a hash, expires quickly, and is atomically consumed once for the initiating user. Provider adapters receive access tokens only in memory and return allowlisted account discovery DTOs. YouTube uses Google authorization-code PKCE with offline consent; the encrypted canonical credential contains the access token, refresh token, expiry, and granted scope, while connected-account discovery persists only channel IDs and display names.
- YouTube access tokens refresh through `getFreshYouTubeCredential`. Refresh is triggered before expiry, writes through the credential repository's optimistic version guard, and reloads the winning encrypted credential when another process rotates first. Provider calls receive only the resulting access token in memory.
- Revocation is idempotent. Reconnect flows update the canonical connection rather than treating credentials copied from another scheduler as portable authorization.
- The authenticated account-management boundary uses `GET /api/provider-accounts` for a tenant-scoped allowlisted summary, CSRF-protected `PATCH /api/provider-accounts/:accountId/youtube-defaults` for owner-managed YouTube destination defaults, and CSRF-protected `DELETE /api/provider-accounts/:accountId` for disconnect. The defaults mutation accepts only the strict YouTube defaults contract and emits an audit event. Disconnect fails with `409` while scheduled, leased, dispatching, or retry-wait jobs still reference the account; it never silently abandons queued work. Disconnection is a soft state transition so historical publication jobs retain their provider-account audit reference, while normal account lists exclude disconnected rows. Removing the final connected account on a provider connection marks the connection disconnected and revokes its credential.
- Browser job recovery uses authenticated, tenant-scoped `POST /api/workflow/jobs/:jobId/cancel` and `POST /api/workflow/jobs/:jobId/retry`. Both require double-submit CSRF and a bounded `Idempotency-Key`. Their repository transitions are state-idempotent: cancellation replays as cancelled, retry replays while already queued, and conflicting lifecycle states return `409` without creating another visible job.
- Browser media previews use authenticated, tenant-scoped `GET /api/workflow/media/:mediaId`. The route resolves only `ready` media through the tenant repository, reads bytes through the canonical `MediaStorage` contract, verifies the persisted byte size, and returns the persisted MIME type with a short private cache policy. Missing and cross-tenant identities are indistinguishable `404` responses.
- Browser create and revision mutations reject scheduled timestamps more than 60 seconds in the past before reserving idempotency state. This named grace exists only for client/server clock skew and the immediate Now flow; it is not a general backdating allowance.
- Browser queue reads may use paired `scheduledAfter`/`scheduledBefore` filters for bounded schedule guidance. Both bounds are required together, the interval must be increasing and no longer than seven days, and the repository applies both predicates before pagination.
- Production runtime secrets are injected by the deployment secret authority, never committed or supplied by clients. `PUBLISH_RELAY_MASTER_KEY_ACTIVE_VERSION` selects a matching `PUBLISH_RELAY_MASTER_KEY_<version>` containing exactly 32 base64-decoded bytes; old versions stay readable until rewrap finishes, while only the active version encrypts. X OAuth uses injected `PUBLISH_RELAY_X_CONSUMER_KEY` and `PUBLISH_RELAY_X_CONSUMER_SECRET`; optional YouTube connection routes require both `PUBLISH_RELAY_GOOGLE_CLIENT_ID` and `PUBLISH_RELAY_GOOGLE_CLIENT_SECRET`. Missing or malformed required production values fail startup without logging secret material.
- `PUBLISH_RELAY_PUBLIC_ORIGIN` is one canonical HTTPS origin. X callback URI is derived as `/api/oauth/x/callback`; request input cannot override it. Connect/reconnect initiation is an authenticated CSRF-protected `POST` deriving tenant and user from the live session. The provider callback requires that same valid SameSite=Lax session, derives tenant authority from it, consumes the one-time hashed request-token transaction, and verifies the session user matches the initiator. Query parameters are correlation material, never workspace/user authority.

## Provider adapter contract

- Provider adapters implement the versioned `ProviderAdapter` contract for connect, discover, validate, stage, publish, lookup, and revoke.
- Adapter contract v1.1 adds the provider-neutral `video` content kind with exactly one media reference and versioned effective YouTube options. YouTube requires a title plus resolved `privacyStatus`, `madeForKids`, and `notifySubscribers`; connection defaults and request overrides must be resolved before the adapter sees the immutable job snapshot. Description, tags, and category remain absent when omitted. The adapter advertises video-only technical capabilities and fails closed until OAuth, resumable-upload, lookup, and revocation transports are configured.
- Core content is an explicit text, quote, or article union with typed media references. Adapters reject unsupported input; they never silently truncate or transform it.
- Publishing returns one typed outcome: published, accepted pending, unknown/reconciliation-required, or failed with auth, rate-limit, validation, transient, or permanent classification.
- Staging is idempotent by caller-supplied key. An unknown publish outcome must be reconciled through lookup rather than retried blindly.
- The X transport uses OAuth 1.0a User Context with credentials supplied only after envelope decryption. It signs native `/2/users/me`, `/2/tweets`, and lookup requests, and never logs or persists token material.
- X does not currently have a proven provider-side idempotency header or create-response correlation key in this product. The scheduler remains the idempotency owner; ambiguous POST transport failures become reconciliation-required with an explicit `x:manual:` marker rather than blind retries. That local marker is never passed to X's exact-post lookup because a job fingerprint is not a provider post ID; only provider-issued post IDs may use automated lookup.
- A live sanitized Daily Viber lookup fixture proves X may return HTTP 200 with a typed resource-not-found error body for a missing post. Lookup treats any successful response without `data` as missing and routes it through reconciliation rather than assuming not-found is always HTTP 404.
- X connection uses the OAuth 1.0a request-token, authorization redirect, verifier callback, and access-token exchange. Request-token secrets must use the encrypted, one-time transaction lifecycle before this flow is exposed by HTTP routes. Revocation and native article publishing remain fail-closed until their provider endpoints and account capabilities are verified. Pre-uploaded media IDs are mapped exactly; media upload lifecycle and limits remain separate evidence-gated work.
- The X OAuth service hashes the request token as callback correlation, encrypts its request-token secret in the provider-neutral OAuth transaction credential, atomically consumes and deletes that one-time secret before exchange, then stores the resulting user credential through the canonical reconnect lifecycle.
- The web boundary exposes authenticated `POST /api/oauth/x` initiation with session CSRF protection and `GET /api/oauth/x/callback` completion. Both derive workspace and user authority from the live session; callback completion consumes only a transaction initiated by that same user. The callback URL is derived from `PUBLISH_RELAY_PUBLIC_ORIGIN`, never request input.
- X's current v2 create-post contract allows at most four media IDs per post, so adapter validation rejects larger target payloads before transport. Official media documentation records 5 MB images, 15 MB GIFs, and 512 MB video with `amplify_video`; upload ownership, chunk persistence, processing status, expiry, and cleanup remain a separate lifecycle slice.
- X media staging reserves one active durable artifact per workspace/job/media before APPEND. The artifact persists its upload phase and next segment so interrupted staging resumes only incomplete APPEND segments. A provider-reference advisory lock serializes APPEND/FINALIZE transitions across processes (with a local test-runtime lock fallback), and STATUS distinguishes an upload that still requires FINALIZE from processing already accepted by the provider. This prevents duplicate chunks and reconciles provider success after a local finalized-state write failure without replaying FINALIZE. Terminal jobs and expired artifacts use the canonical provider-staging cleanup lifecycle. The credential-bound `XHttpClient` is the production staging client: it OAuth1-signs form-encoded INIT/FINALIZE, multipart APPEND, and query-encoded STATUS against the native upload endpoint; status processing honors provider check delays with a bounded poll count, and provider errors retain only safe classification and retry timing.
- Provider staging keeps provider session secrets out of plaintext reference columns. Secret resumable references are envelope-encrypted in the canonical `credentials` table and attached through a workspace-composite foreign key; byte-oriented adapters persist their provider-confirmed next offset and terminal external object ID beside the existing segment-oriented X cursor. Repository mutations always include workspace and active-artifact predicates.
- YouTube resumable staging reserves the canonical artifact and attaches its envelope-encrypted Google session URL in one tenant transaction. Every resume holds the shared provider-staging advisory lock, reloads durable state, queries Google for the authoritative byte offset before sending another chunk, persists every provider-confirmed cursor and terminal video ID, and clears decrypted session/media buffers in `finally`. A durable terminal video ID short-circuits all later provider calls.
- The YouTube HTTP boundary emits typed upload failures (`auth`, `quota`, `validation`, `transient`, or `permanent`), preserves bounded `Retry-After` evidence, and marks transport failures after a resumable PUT begins as unknown outcomes. Callers must query the durable session before any retry; they may never blindly replay an ambiguous chunk.
- Google does not expose a delete endpoint for an untracked resumable session. If Google accepts initiation but the credential-and-reference transaction rolls back, the durable artifact intentionally remains without a credential; retry creates one replacement session under the same artifact lock. The inaccessible first session receives no video bytes and expires at Google's provider-managed session lifetime, bounding the only unavoidable remote residue.
- The worker entrypoint owns the complete scheduled X dispatch path for text-only and media jobs. It claims due jobs, loads immutable revision content plus ordered media and account connection under tenant RLS, decrypts credentials only in memory, and completes or resumes media staging before opening the canonical scheduler attempt. Pending media never publishes early; ready jobs pass staged provider media IDs through `XProviderAdapter`, and every typed result closes the attempt through scheduler state/audit ownership. Before claiming new work, the worker recovers expired dispatch leases into reconciliation, claims those jobs, and uses adapter lookup so ambiguous outcomes are never blindly republished. Media bytes resolve beneath the configured local storage root with traversal rejection; decrypted buffers are zeroed after each dispatch or reconciliation pass.
- Native X threads preserve ordered `content.kind=thread` parts. Legacy string parts attach revision media to the root; object parts may explicitly assign revision `mediaIds` per part, including an empty root assignment. Before each provider call the worker inserts a unique tenant-scoped `x_thread_parts` dispatch intent, then promotes it to `published` with the provider ID and URL. A definite provider rejection removes only its matching still-dispatching intent so bounded retry may resume; an ambiguous create outcome retains the intent and fails closed because X create exposes neither a provider idempotency key nor lookup correlation. A published contiguous prefix resumes at its first missing part, so retries never duplicate confirmed predecessors. Job-level `external_post_id` remains the root identity while ordered part IDs and URLs live in the thread ledger.
- X's current v2 Articles API documents OAuth 1.0a User Context support for draft creation and publication, but Daily Viber account entitlement and the required DraftJS conversion have not been proven. Article publication therefore remains fail-closed until a separately authorized capability canary and explicit content-conversion contract exist.

## Social God shadow parity

- `npm run remediate:x -- dry-run --workspace-id <uuid>` is the bounded Daily Viber incident verifier. It is hard-limited to the five approved job/post pairs, loads normalized revisions and media hashes under tenant RLS, decrypts the job-bound X credential only in memory, and performs read-only X ownership lookups. Live mutation remains unavailable until Oracle and Overseer authorize the canary.
- Live remediation journals intent phases before each provider mutation. Delete replay first looks up the old provider ID and may safely finish an already-applied delete. Replacement intent creation and `replacement_job_id` persistence share one tenant transaction; replay always resumes that exact job through exact-job dispatch/reconciliation and never creates a second replacement. A provider-published attempt is recovered from the persisted job before any dispatch call because X has no proven create idempotency key.
- The live remediation gateway requires one exact allowlisted job/post pair and `LIVE_CONFIRMATION`. Pairs advance strictly in allowlist order: every preceding journal must already be `verified`. Before entering the delete phase it reads each canonical local media object and verifies its bytes against the immutable source SHA-256. It creates replacements through the canonical post-intent lifecycle and uses the scheduler's exact-job claim path. It never runs the general due-job claim, so unrelated queued work cannot dispatch while the normal worker remains unloaded.
- Replacement dispatch first recovers any durable published attempt for the persisted replacement job. Only an exact-job dispatch may follow; a missing published attempt after that boundary fails closed, and replay must return the durable attempt rather than call the provider again.

- `src/modules/parity/social-god.ts` is the credential-free boundary for Social God Daily Vibe snapshots. It accepts bounded package, `schedule_records`, account-map, media-map, and explicit item-to-package-map JSON; it never reads either product database or provider configuration. Current raw schedule rows join through `item_id` to either the package's `postiz_notes.cms_item_id` or the explicit map; synthetic `package_id` fields are not required.
- `npm run parity:social-god -- <snapshot.json>` emits the Publish Relay v1 request/CLI, fake-provider outcome, source result, and exact unresolved gaps. Output is always marked dry-run with credentials unused and external writes blocked.
- `npm run schedule:social-god -- <snapshot.json>` is the canonical cutover entrypoint. It defaults to dry-run; `PUBLISH_RELAY_SCHEDULER_TARGET=publish-relay` explicitly enables submission through the v1 API using runtime-injected base URL, workspace, and API key. It validates the complete snapshot before any mutation, performs a workspace preflight, reuses parity-generated bodies and idempotency keys, and emits only bounded Relay identities. Existing Postiz rows are outside its lifecycle.

- `/agents.txt`, `/publish-relay-skill/SKILL.md`, `/publish-relay-skill/publish-relay-cli.js`, and `/publish-relay-skill/manifest.json` are public, tenant-neutral discovery assets. They must never contain credentials, account data, runtime configuration, or live IDs.
- The manifest carries distinct discovery-contract and CLI versions, checksums the exact served agents, skill, and CLI bytes, and advertises CLI updates as warn-only. All four routes use the same explicit public cache policy. Agents read the skill and API contract before use; the product never self-updates an installed client.

## Content and media persistence

- Streamed uploads stage mode-0600 files under the local storage `.temporary` namespace. The worker reconciles this namespace on startup and every 60 seconds, removing only files older than `MEDIA_STAGING_STALE_MS` (24 hours by default); web startup performs the same idempotent sweep. Concurrent sweepers tolerate entries that disappear between enumeration and inspection, preserving fresh/in-flight uploads while deterministically bounding crash-orphan retention.

- `posts` owns mutable publication intent while `post_revisions` records immutable, numbered content snapshots. The database rejects revision update and deletion.
- Post and revision actor columns persist the authenticated user or named API key identity; `api_key` is identity while CLI is optional transport metadata only. Nullable actor columns are the explicit legacy/unknown state. Canonical job detail projections resolve safe actor labels and include ordered revision media, attempt/activity history, and the latest provider result.
- `revision_media` links ordered workspace media to a revision. `publication_jobs` creates one independent account target per revision, and `provider_staging_artifacts` records temporary provider-side resources that require deterministic cleanup.
- Every content/media table is workspace-scoped with explicit repository predicates and forced RLS. Media identity records a storage key plus byte-derived SHA-256, MIME type, and byte size; application services must not trust client metadata for those fields.
- The durable worker runs bounded media-retention cycles across workspaces. `MEDIA_RETENTION_DAYS` is an optional neutral self-hosted policy (omission retains forever); cadence, retry, stale-claim recovery and batch size are operator configuration. Revision creation locks referenced media and revives eligible/failed retained bytes, while cleanup locks candidates and atomically rechecks active job references before physical deletion.

## Usage facts and provider capabilities

## Destination-scoped provider defaults

- `provider_accounts.adapter_defaults` is the destination-scoped source for optional provider policy defaults; it never stores credentials.
- The browser account-management summary includes `adapterDefaults` only for its authenticated owner-facing settings form; the public/API-key destination collection remains a smaller contract and does not expose defaults.
- Scheduling resolves sparse request overrides against those defaults before inserting target jobs. Each `publication_jobs.effective_provider_settings` value is the immutable, complete provider snapshot used for dispatch and returned by job-facing contracts.
- YouTube resolution is owned by `src/modules/providers/youtube-settings.ts`: public and `notifySubscribers=false` are product defaults, `madeForKids` must resolve from either the destination or request, and omitted tags/category remain absent.
- `src/modules/providers/youtube-http-client.ts` owns Google token exchange/refresh/revocation and exact owned-channel discovery behind an injected HTTP boundary; persistence services encrypt its credential value and serialize refresh writes.
- Revisions keep caller content; target-specific effective settings belong to the independent job so multiple destinations may resolve differently without mutating shared revision history.

- `getWorkspaceUsageFacts` is the sole transactional owner of workspace usage facts for policy and application consumers. It derives retained media bytes and lifecycle counts, active connected accounts/provider families, publication-job target rows, active queued targets, scheduling horizon, and membership count from canonical Core tables under tenant RLS.
- A publication target fact is one `publication_jobs` row, including historical rows; multiple jobs aimed at one connected account remain multiple targets. Connected-account facts require both a non-disconnected account and an active parent connection. Deleted media remains visible in lifecycle counts but contributes no retained bytes.
- Provider capability metadata stays adapter-owned and describes technical content/media shapes, target behavior, dispatch mode, and verified provider limits only. It must not contain plan names, prices, entitlements, or commercial admission rules. Neutral action policy consumes these facts rather than re-querying tables or teaching adapters about commercial policy.

# Agent destination discovery

## External draft handoff

- `external_drafts` is the durable tenant-scoped handoff aggregate for authorized external applications. Identity and canonical replay are keyed by workspace, authenticated actor type/id, and the caller's opaque `external_id`; `request_fingerprint` detects changed-input conflicts without overloading the generic mutation-replay ledger.
- `external_draft_media` is the only draft-to-media attachment owner. Its workspace-composite foreign keys prevent cross-tenant attachment, preserve caller ordering, and keep the canonical `media_objects` lifecycle reusable. A draft may transition once to a canonical post through its optional workspace-bound `post_id`; provider, destination, schedule, and publication metadata do not belong on import drafts.
- Both tables use forced tenant RLS. Application boundaries validate optional return URLs as HTTPS and derive source actor/client identity from authentication rather than request fields.
- `src/modules/content/external-draft.service.ts` owns validation and canonical replay/conflict behavior; its repository owns the transactional aggregate, ordered attachments, and creation audit. `POST /api/v1/drafts` and `GET /api/v1/drafts/:draftId` require `content:write`, expose only the draft contract and stable relative links, and safe-404 drafts owned by another workspace or machine principal.

## Delegated client authorization

- `src/modules/delegated-authorization/protocol.ts` is the provider-neutral protocol boundary for registered clients. Authorization requests require a non-empty client state, exact redirect-URI allowlisting, PKCE S256, and a non-empty subset of the client's registered scopes.
- Authorization codes, access tokens, refresh tokens, and confidential-client secrets are opaque random values. Durable storage receives only SHA-256 hashes; comparison uses constant-time equality. Codes expire after five minutes and access tokens after fifteen minutes unless a later owner-approved contract changes those named constants.
- Open Clips is the initial registered client, not a schema or route owner. Client-specific redirect URIs and scope allowlists are configuration/data, while grant lifecycle, exchange, rotation, revocation, and audit behavior remain generic Relay responsibilities.
- Migration `0033_open_clips_development_client.sql` owns the exact local development registration: public client `open-clips-dev`, callback `http://127.0.0.1:43123/callback`, and the bounded scopes `destinations:read schedules:read schedules:write content:write publishes:retry`. Production callback registration is a later environment-specific data migration; wildcard, arbitrary-port, and client-supplied callback registration are forbidden.
- `registered_clients` owns global client identity and exact redirect/scope allowlists. `delegated_grants` owns one active user-approved client connection per workspace; a revoked grant remains as history and reconnect creates a new grant without touching unrelated API keys.
- `delegated_authorization_codes` and `delegated_tokens` are grant-owned, workspace-scoped credential ledgers protected by forced RLS. Hash uniqueness is global, authorization codes are single-use through `consumed_at`, refresh rotation links the replacement to its predecessor, and grant revocation invalidates every descendant credential.
- `DelegatedAuthorizationService` is the protocol orchestration boundary. It validates registered clients before approval, passes only hashes and the derived PKCE challenge to persistence, and requires atomic store operations for code verification/token issuance and refresh rotation. HTTP routes and API authentication must call this service rather than reproducing PKCE, expiry, hashing, or rotation rules.
- Delegated clients use the existing `/api/v1` resource contract with `Authorization: Bearer <access-token>` and the explicit `X-Publish-Relay-Workspace` preflight. Capability guards, action policy, idempotency, audit attribution, rate limits, and tenant hiding are shared with API keys; clients must not infer a separate delegated API surface. Clients verify callback state, exchange codes server-side, encrypt token responses at rest, rotate refresh tokens, and treat Relay-side grant revocation as terminal reauthorization.
- Authenticated `GET /api/v1/account` is the canonical machine connection receipt. API-key output remains unchanged; delegated bearer output allowlists only `principalType=delegated`, client/grant/workspace identity and label, granted capabilities, and access-token expiry. The resolver derives that receipt from active token/grant/workspace rows without exposing user identity or token material, and the response is never cached.
- `src/modules/delegated-authorization/delegated-authorization.routes.ts` is the generic HTTP boundary. Browser navigation to `/connect/authorize` serves the authenticated consent shell or redirects to login with a same-origin continuation; JSON negotiation on the same URL validates the registered client before presenting consent. Approval binds to the authenticated session workspace/user, requires CSRF, and returns either the protocol redirect or a JSON redirect instruction for the SPA. `/connect/token` accepts only authorization-code or refresh-token grants and emits stable OAuth-style error fields with `Cache-Control: no-store`; callback redirects contain only the short-lived authorization code and exact client state. `POST /connect/revoke` accepts a client's own access or refresh token plus client ID (and the registered secret for confidential clients), atomically revokes that grant family, and returns an opaque idempotent empty 200 for unknown/already-revoked tokens; all responses are `no-store`. `GET /api/settings/delegated-grants` returns at most 100 active grants owned by the authenticated workspace/user, projected to grant ID, client ID, scopes, and creation time; token material, internal ownership fields, and revoked history are absent. User revocation is a CSRF-protected, tenant-bound settings mutation and never touches unrelated API keys.
- Opaque delegated credentials resolve through three narrowly granted `SECURITY DEFINER` database functions with a fixed search path. They accept hashes (plus the derived PKCE challenge for exchange), return the minimum grant principal, preserve forced tenant RLS on all tables, and own the atomic verify-consume-issue/access-touch/refresh-rotation mutations. Function privileges belong only to the canonical `publish_relay_web` authority and are applied by database bootstrap after roles exist; migrations must remain fresh-install safe when fixed roles have not been created yet. Application SQL must never disable RLS or accept a caller-supplied workspace as credential authority.
- `createPostgresDelegatedAuthorizationStore` is the only application adapter for delegated grant/code/token persistence. Tenant-known mutations use the canonical tenant transaction; opaque credential resolution calls only the audited hash-based functions above.
- Grant approval and revocation write `delegated_grant.approved` and `delegated_grant.revoked` audit events in the same tenant transaction as the lifecycle mutation. The authenticated user is the actor, the grant is the target, request correlation is retained, and approval metadata contains only client ID and approved scopes.

`GET /api/v1/destinations` is the canonical account-scoped discovery surface for API customers. It requires `destinations:read` and returns only the provider-account ID, provider, display name, connection status, and update timestamp. Credential IDs, connection IDs, provider metadata, defaults, ownership fields, and secret material are never exposed by this collection contract.

`POST /api/v1/jobs/:jobId/retry` is the canonical agent retry surface. It requires `publishes:retry`, an idempotency key, and a tenant-owned failed job whose outcome does not require reconciliation. The API-key identity is retained as the policy and event actor; unknown outcomes must be reconciled rather than blindly retried.

Provider runtime registration is isolated: missing provider-specific credentials disable only that provider and emit a secret-free `provider_disabled` event. Common worker prerequisites may still fail startup, but one provider's absent configuration must not prevent unrelated providers or retention/reconciliation infrastructure from running.

# Browser create response

The due-job claim boundary enforces one hard missed-post rule before leasing: a still-scheduled job more than 30 minutes late transitions to `needs_review`, retains its original `scheduled_at`, creates no publication attempt, and is never automatically rescheduled. A job exactly 30 minutes late remains eligible. Both batch and exact-job claim paths use the same rule.

Production releases probe readiness only after both systemd units restart. The canonical release script uses a bounded configurable retry window (12 attempts, two seconds apart by default), retains curl's fail-closed behavior, and exits nonzero after exhaustion so deployment orchestration can invoke the existing rollback path rather than treating a late or failed startup as success.

- Browser post creation returns bounded job summaries containing only job ID and persisted `effectiveProviderSettings`, so clients can retain the resolved destination-default snapshot without reconstructing it.
- Browser Composer uploads remain unattached until post creation succeeds. Its authenticated CSRF-protected media delete endpoint atomically tombstones only tenant-owned ready media with no revision reference, then removes the local object; attached media is never deleted through this abandonment path.

## Release-artifact retention

- `src/modules/operations/release-retention.ts` is the single read-only policy owner for current plus three explicitly verified database-compatible rollback releases and unlimited migration/recovery pins. It is separate from tenant media retention and never deletes artifacts.
- `release-retention.contract.ts` validates inventory/evidence and binds receipts to exact filesystem/runtime/database state; stale, mismatched, failed-deploy, unverified, or insufficient-rollback evidence keeps everything. `release-inventory.ts` performs strict read-only filesystem and actual systemd process observation; existing deploy/rollback lack shared serialization, so it cannot attest a prune-safe state.

The compiled `release-retention` entrypoint has inspection, assessment, and offline proposal modes, no apply path, and no runtime integration. ## Database-backup retention

- `deploy/backup-database.sh` owns private staging, exclusive capture locking, full `pg_restore` archive traversal, mandatory age round-trip comparison through a disposable verification recipient, and atomic no-clobber publication with an exact SHA-256/size validation receipt. Ordinary failure cleans only its staging and never prunes; crash-orphaned state needs owner inspection.
- `src/modules/operations/backup-retention.ts` is the read-only UTC three-daily plus 7/30-day policy owner, including bridge copies and additive migration/recovery pins. Missing coverage/pins keeps everything; invalid or unreceipted archives never satisfy coverage. `backup-inventory.ts` binds local validation receipts to exact encrypted bytes without following symlinks.
- The compiled `backup-retention inspect` entrypoint emits exact advisory manifests only, with empty approved deletion paths and no apply/deploy integration. `deploy/BACKUP-RETENTION.md` defines the conservative age windows, bridge rotation, ephemeral verification-key lifecycle and separate isolated-restore/off-host/live-approval gates. No schema, API, provider, scheduler or tenant-media changes occur.
