# Publish Relay deployment

Production uses immutable releases under `/opt/publish-relay/releases`, an atomic `current` symlink, and separate hardened systemd web and worker units. Web secrets belong in root-owned `/etc/publish-relay/publish-relay-web.env`; worker secrets belong in `/etc/publish-relay/publish-relay-worker.env`. Both are injected from the approved vault and never belong in a release. The deployment-only `MIGRATION_DATABASE_URL` is supplied to release, backup, and restore tooling without placing it in either runtime environment file.

## Database authorities

Provision the fixed `NOLOGIN` group roles with `bootstrap-database-authorities.sql` as a PostgreSQL administrator, then create separate secret-bearing login roles outside source control and grant each login exactly one group role. `DATABASE_URL` must authenticate as the web login granted `publish_relay_web`; `WORKER_DATABASE_URL` must authenticate as the worker login granted `publish_relay_worker`. Each entrypoint starts its connections with `SET ROLE` through PostgreSQL startup options, so group authority—not login-role attributes—is the effective runtime authority. The worker group alone has `BYPASSRLS` for cross-workspace claim/recovery queries. Scheduler code must return to `withTenantTransaction` for every workspace-specific mutation. The migration login is separate and must not be used by either runtime unit.

Run the bootstrap again after forward migrations so grants cover newly created tables and sequences. The script is idempotent. Verify with `SELECT rolname, rolbypassrls FROM pg_roles WHERE rolname LIKE 'publish_relay_%'`; only `publish_relay_worker` may report `true`. Do not put login passwords in the SQL file, release, unit, or deployment ticket.

Deployment order is build artifact transfer, `publish-release.sh`, production-dependency install, compiled forward migration, atomic symlink switch, unit restart, and readiness verification. A failed migration stops before the symlink changes. The release must contain `dist/database/migrate.js`; production deployment never depends on the development-only `tsx` runtime. Application rollback uses `rollback-release.sh`; migrations must remain backward compatible under the expand/migrate/contract rule.

Install an isolated Node 24 toolchain under `/opt/publish-relay/node24` before the first release. `publish-release.sh` fails closed unless `PUBLISH_RELAY_NODE_BIN` is executable, reports Node 24, and `PUBLISH_RELAY_NPM_CLI` is present; defaults point to the isolated Node binary and its `lib/node_modules/npm/bin/npm-cli.js`. The script invokes that npm CLI through the selected Node binary, so an `env node` launcher cannot fall back to host Node 22. The absolute Node path is pinned directly in both systemd `ExecStart` commands. Preflight with `/opt/publish-relay/node24/bin/node --version`, which must report `v24.x`.

`backup-database.sh` creates an age-encrypted custom-format PostgreSQL backup with a 14-day default retention. Backups and migrations require `MIGRATION_DATABASE_URL`, never either runtime URL. `restore-drill.sh` uses that production authority only for target protection and requires an isolated `RESTORE_DATABASE_URL`; it rejects the production database by URL or database name and requires the restore database name to end in `_restore` or `_restore_drill` before running destructive `pg_restore --clean`. After restore, run the authority bootstrap against the isolated target before application verification. It then proves the migration ledger is readable. Operators must record the backup path, restore database, row-count checks, elapsed time, and cleanup in the deployment ticket without copying secrets.

Reverse proxy TLS termination must forward only to the isolated Publish Relay listener, initially `127.0.0.1:3106` (`HOST=127.0.0.1`, `PORT=3106`). `publish-release.sh` probes `PUBLISH_RELAY_HEALTH_URL`, defaulting to `http://127.0.0.1:3106/health/ready`. Keep `/metrics` restricted to host monitoring. Verify `/health/live`, `/health/ready`, login, protected-shell redirect behavior, worker restart survival, process metrics, journald logs, and absence of changes to existing services before cutover.
